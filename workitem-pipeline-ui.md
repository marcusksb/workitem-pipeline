# Workitem pipeline UI — design

## Goal

A local web UI to see and steer workitems across projects, and to attach a browser terminal to an agent session when it is blocked. Backend in Rust, frontend in React. Builds on `workitem-pipeline.md`; the pipeline stays the source of truth.

## Decisions

1. **Access:** localhost only. Bind `127.0.0.1`, fixed port (default 7373, overridable).
2. **Auth:** persistent random token, generated on first run and stored in `~/.config/workitem-ui/config.toml` (mode `0600`). The backend prints `http://127.0.0.1:<port>/#token=…`. The page posts the fragment once to `/api/login` and gets an `HttpOnly; SameSite=Strict` cookie. Every API call and WebSocket upgrade checks the cookie; the WebSocket also requires `Origin` to equal the server's own origin. `workload --rotate-token` replaces the token.
3. **State:** the backend reads `<repo>/.claude/workitems/<dir>/workitem.md` directly. It never writes `stage:` itself. Every stage change runs `bin/workitem-move <full path to workitem.md> <stage>`, so the transition and brief rules live in one place.
4. **Projects:** listed in `config.toml` (name, repo dir). The UI can add and remove projects. Removing a project only drops it from the config.
5. **Terminal:** the backend opens a PTY (`portable-pty`) running `tmux attach -t wi-<dir>` and bridges it over a WebSocket to xterm.js. Closing the tab kills the attach client only; the session and agent keep running. The session name is built from a known workitem, never from raw input.
6. **Live data:** the browser polls `GET /api/workitems` every 3s. The backend re-reads frontmatter and runs `tmux list-sessions` per call. No cache, no push.
7. **Session naming:** keep `wi-<dir>`. A session belongs to a project when its `@workitem_repo` option (set by the launcher in the same tmux call that creates it; `#{session_path}` for sessions without it) equals the project's repo dir. A workitem's session starts in its worktree `../<repo-name>-<dir>` when git has one, with `claude --add-dir <repo>` so the agent can still edit `workitem.md`; otherwise in the repo. The UI refuses to start a session if `wi-<dir>` already exists and names the conflicting repo.
8. **Actions.**
   - Direct in the backend: approve (`approved: true`, `approved_at`), reject with comment (back to `analyze`), clear blocked, kill session. Deterministic, no tokens. Clear blocked sets `working` when the session is still alive (the agent waits for its answer; `ok` would make the dispatcher kill it) and `ok` otherwise. Kill session ends the session and sets `ok`, so the dispatcher retries or stops at the attempt cap.
   - Through tmux agents, same pattern as `workitem-run` step 4 (`claude --settings …/hooks.json "<prompt>"`, `remain-on-exit on`):
     - start: `wi-<dir>` running `workitem-start`
     - discuss brief: `wi-<dir>` with a prompt that opens on the brief and plan, in any stage. The human talks it through; the agent edits the brief only on request and never touches `stage:` or `approved:`
     - create: `wi-new-<id>` running `workitem-create` (input: Jira key, Sentry URL or text)
     - remove: no agent. The backend stops the item's `wi-<dir>` session (this project's only), runs `bin/teardown_worktree` if the worktree has one, `git worktree remove` (never `--force`; if git refuses the worktree is left and reported), then deletes the folder, all before the request returns, so the dispatcher never sees a half-removed item. Works in every stage. Branch and PR stay. A final column (a stage whose `next` is empty on every project in view, e.g. `done`) has a "Clear" button in its header that runs this remove for each of its items, one after another, and lists any that failed.
   - User-typed text goes to `claude` as an argv element, never through a shell string. `<dir>` is validated against known workitems.
9. **Dispatcher** (the handler start and the PR rules below now live in the `run-items` and `pr-review` watch scripts, see 32; `dispatch.json` is no longer written, and the attempt counts are item frontmatter): a Rust reconcile loop owns `backlog`, `analyze` and `in_development` (`workitem-start` gets the start prompt, since it writes code). It applies `workitem-run` steps 1 to 4: reap finished sessions, skip `blocked` items, cap attempts at 3 then set `blocked: max attempts reached in stage <stage>`, start `wi-<dir>` with the handler prompt. State file `dispatch.json` next to the config (the skill's file lives in a Claude session scratchpad, which the backend cannot see). It reconciles every 5s and immediately after any UI action, so a new item, a stage change or an ended session is picked up within seconds. A pass reads a few small files and one `tmux list-sessions`, so it costs no tokens when idle. Idle passes cost no tokens. An approved item in `ready_for_development` is started right away with the `in_development` handler (approving wakes the loop). `in_review` (`workitem-watch`) is not dispatched as a skill; the dispatcher owns the PR status and four fixers (`review.rs`): at most once a minute per item it runs `gh pr view <pr url>` (no tokens) and keeps approval, merge and CI status in memory for the board's chips. A merged PR moves the item to `done`; a closed one blocks it. Red CI (once every check other than `dockerized|e2e|playwright` has settled) starts a fixer session `wi-<dir>` that fixes, pushes and sets `ok`, or sets `blocked: <reason>` and waits for the human in the session. Attempts cap at 3 per red streak, then `blocked: CI still failing after 3 fix attempts`; green CI resets the count. A merge conflict starts a `wi-<dir>` session that rebases onto the base branch, resolves only obvious conflicts, and force-pushes with lease after tests and lint pass; otherwise it sets `blocked` and waits. It runs once per PR head sha (`conflict_head` in `dispatch.json`), so a fixer that gave up is not retried until someone pushes. A `CHANGES_REQUESTED` review starts a fixer once per review id (`handled_review`); in one pass, CI goes first, then the conflict, then the review. Neither has an attempt cap, since one head or one review starts one fixer. Comments that ask for a change are last in the pass: inline comments from others, `COMMENTED` reviews from others that have a body (ids `review-<id>`), every PR comment from others (bots included, since review bots such as Quality Risk Review post their findings as one), and the reader's own comments with `@change` or as a new inline thread (not a reply). Detection is one `gh api` call for the inline ones (the PR comments come with the poll) and only runs while the item is idle. A batch of new ones starts one `wi-<dir>` fixer; `comment_mark` in `dispatch.json` is the creation time of the newest one handled, and the first reading of an item only sets it, so comments already on a PR are not new. `/loop /workitem-watch` would fix all of these too, so do not run it beside the UI. `/loop /workitem-run` is turned off for auto stages once this ships; two runners would race.
10. **Notifications:** the frontend fires a browser notification and a beep when polling shows an item newly `blocked`. It needs an open tab and one click per page load for sound and permission.
11. **Lifecycle:** no service. You start the backend from your shell; the dispatcher runs while it runs. State is on disk and tmux outlives the backend, so a restart re-reconciles.

Sessions without a workitem (`wi-new-*`) are listed in an "Agent sessions" strip with a pop-out terminal link, because a blocked create session can only be answered by attaching. Env overrides: `WORKITEM_UI_PORT`, `WORKITEM_UI_CONFIG`, `WORKITEM_UI_TMUX_SOCKET`, `WORKITEM_UI_SKILLS` (default `~/.claude/skills`), `WORKITEM_UI_CLAUDE` (default `claude`), `WORKITEM_UI_GH` (default `gh`), `WORKITEM_UI_DISPATCH=off`.

## Configurable boards (planned)

Each project can define its own boards: the columns, and what each column's watcher does. Decisions 12 to 27 extend the list above. Once built they replace the hardcoded paths and stage names in decisions 3, 8 and 9. The file format is in `workitem-pipeline.md`.

12. **Location.** Items and config live in `<repo>/.workitems/`, not under `.claude/`, so the pipeline is not tied to Claude. If `.workitems/` does not exist, `<repo>/.claude/workitems/` is read instead, so existing projects keep working. `workitem-migrate` moves an old folder over; nothing migrates by itself. The path is built in one place per language (`workitem-move`, `workitem.rs`).
13. **Scope.** Boards are per project and configured by file only; there is no editor in the UI. A project's board file replaces the bundled `skills/workitem-pipeline/pipeline.json` in full, with no merging. A project without a file uses the bundled one.
14. **Format.** `stages` is an ordered array and its order is the column order. `label` is optional and defaults to the name with `_` shown as a space.
15. **Handlers** (a stage with a `prompt` and no `handler` is dispatched like a skill stage). A stage has one of: a skill name (`handler`), `handler: "builtin:pr-review"`, an inline `prompt` string, or neither (a manual column). Having both `handler` and `prompt` is invalid. `prompt` is a plain string, started like a skill (same tmux session, attempt cap and `ok`/`blocked` handling, argv element, no shell); anything long should be a skill. Shell commands and `prompt_file` are out.
16. **Roles, not names.** The backend, UI and `workitem-move` no longer know stage names. A closed set of keys carries the roles: top-level `entry` (where new items start); `gate` (below); `on_merge` (on the `builtin:pr-review` column, the stage a merged PR moves to); `require` (`issue: "linked"` and `brief: "complete"` are checks, replacing the Jira and Review brief rules hardcoded for `ready_for_development`; any other key compares a frontmatter value, as before). `next`, `auto` and `on_enter` keep their meaning.
17. **Gates.** `gate: {label, approve_to, reject_to}` is a column where a human decides. The button shows `label`. Approving sets `approved: true` and `approved_at`, then moves the item to `approve_to` with `workitem-move` (a refused move puts `approved` back to false); rejecting (with a comment) moves it to `reject_to`. Both targets must be in the stage's `next`. A board can have any number of gates. There is no separate start stage: the dispatcher runs the handler of whatever stage `approve_to` names, so the `in_development` hardcode in `dispatch.rs` is gone. A gate gives items without a PR a way to reach the end, for example "Implementation approved" with `approve_to` the last stage. The "Start development" action is offered for an approved item whose stage has the handler `workitem-start`.
18. **PR watcher.** The handler `builtin:pr-review` is the existing `review.rs` (poll, chips, fixers, merge). At most one per board, and it needs `on_merge` (the stage a merged PR moves to, in the stage's `next`), which no other stage may have. Builtin handlers are never started as sessions. The PR chips and PR actions show on that column, whatever it is called. The API tells the UI what a stage allows (`gate`, `pr_watch`, `develops` on each item), so the UI knows no stage names. An `on_commit` watcher is out for now and can be added later as another builtin.
19. **Handler context** (built; `launch::stage_context`). The launcher adds a block to every handler prompt, skill or inline: the workitem path, the current stage, and the allowed `next` stages (the first is the default forward move). Handler skills move to "the default next stage" or the stage the prompt names instead of naming stages themselves. `workitem-move` still enforces every rule.
20. **Mismatches.** An item whose stage is not on its board shows in an extra "unknown stage" column at the right end, flagged, and the dispatcher skips it; `workitem-move` can still move it, but only to the board's `entry`. An invalid board file (bad JSON, a `next` or role pointing at a missing stage, no `entry`, both `handler` and `prompt`, two `builtin:pr-review`) is rejected as a whole: the last good config stays in use, the board shows an error banner and the reason is logged. The dispatcher never runs on a half-valid file. A missing file falls back to the bundled one.
21. **Several boards per project.** `.workitems/pipeline.json` is the `default` board; further boards are `.workitems/boards/<name>.json`, and the board id is the file name. Items stay flat in `.workitems/<dir>/`; an item picks its board with `board: <name>` in its frontmatter, and a missing key means `default`. `workitem-move`, `workitem.rs` and the dispatcher load the board named by the item. `next` only names stages of the same board.
22. **Creating and switching.** `workitem-create` takes a board (default `default`); the UI's create dialog pre-selects the board on screen, and the item starts at that board's `entry`. `workitem-move <path> --board <name>` is the only way to change `board:`: it lands on the target's `entry` (running its `on_enter`), resets the attempt counter like any stage change, and is refused while the item has a live session. There is no stage mapping between boards. The command line is the only way to switch for now; the detail panel has no button for it. `/api/pipelines` lists each project's boards (`default` first, then by name), and `POST /api/projects/<p>/create` takes an optional `board` that must be one of them.
23. **Board tabs.** The UI shows one board at a time, with a tab per board (hidden when a project has one board). Each tab carries a badge with its number of blocked items. The selected board is part of the hash, as `?board=<name>` after the item path (`#app/x-1/pr?board=research`, or `#?board=research` with no item). An unknown or missing board in the hash shows the first tab. An item whose `board:` has no file goes into an "unknown board" bucket on `default`, so it never disappears: it is shown in the unknown-stage column, whatever its stage is called.
24. **Approval per gate.** Entering a gate clears `approved` (`on_enter`), and approving sets it and moves the item. A later stage that needs the flag asks for it with `require: {approved: "true"}`; nothing relies on one flag staying set across the board.
25. **Left out for now.** An in-UI board editor, `on_commit` or other new builtins, `prompt_file`, shell-command handlers, partial overrides of the bundled file, automatic stage mapping between boards.

28. **Limits and queues.** `limit` on a stage is enforced by `workitem-move` (it counts the other items of the same board in that stage) and by nothing else, so a manual move and the dispatcher meet the same rule. A stage that is `auto` with no `handler` and no `prompt` is a queue: it is watched by the bundled `watch/pull-queue` script (written into the stage as a `watch` every 5s when the file does not name one): it moves the stage's idle items (`ok`, no session) to `next[0]` through `workitem-move`, ordered by `created` and then by directory name, and stops at the first refusal. A board can name its own watch (a different `every`, or its own script) on such a stage.
29. **`once` and `when`.** A handler stage with `once: true` starts at most once per entry (the attempt counter, which a stage change resets, is the memory), so a stage with `next: []` does not restart its handler every pass. `when` is a map of frontmatter values that must all match before the handler starts, for example `approved: "true"` on a stage that a gate's reject also leads to.
30. **`pr_status`** (superseded by 40: the key now only makes the board read its PRs). A stage with `pr_status: true` gets the PR chips on its cards without being the `builtin:pr-review` stage, which also starts fixers and merges. After each pass `review::refresh_due` reads the PR of idle-or-not items in such stages with `gh pr view`, at most 5 per pass and each at most every 5 minutes (five times the PR stage's interval), and keeps the result in the same map the API reads. Merged or closed PRs drop their chips. For reviewing other people's PRs.
31. **PR review board** (a project's own board, plan in `pr-review-board-plan.md`). The queue, the limit and a gate whose approve and reject both lead to the final stage are built from the keys above; the intake of PRs is a skill run on a loop, outside the backend, so Jira/Sentry/PR polling stays a non-goal of the backend itself.
32. **Column watchers** (built; `watch.rs`). A stage can carry `"watch": {"every": "1d", "command": "age-out", "args": ["--older-than", "30d", "--delete"]}`: a script the dispatcher starts when `every` (`30s`, `10m`, `2h`, `1d`) has passed since its last start, whether or not the column has items. The rules live in the script, not in the backend: moving, deleting or creating items is the script's job, through `workitem-move` and the workitem files. The script is a file found in `<workitems dir>/boards/<board>/watch/`, then `<workitems dir>/watch/`, then the bundled `watch/`, and is run directly, never through a shell. It gets `WORKITEM_{REPO,DIR_ROOT,BOARD,STAGE,NEXT,MOVE}` in the environment and the column's items as a JSON array on stdin, runs in a task of its own (one at a time per watcher, killed after 10 minutes) and costs no tokens. Last start times are in `watch.json` next to the config, so a restart does not rerun a daily script. The dispatcher's "start the handler" half is the bundled `watch/run-items` (`auto` stages with a handler or prompt get it implicitly, every 5s): it skips items that are not `ok`, have a session, or miss the stage's `when`, honors `once`, counts attempts per stage entry in the item's frontmatter (`handler_attempts`, which `workitem-move` drops on every stage change) and sets `blocked: max attempts reached in stage <stage>` after 3 (`--max-attempts`) or `blocked: <reason>` when `workitem-run-item` exits 2 (handler not found). Reaping finished or crashed sessions stays in `dispatch.rs`. Only scripts that cannot be shared between projects belong in a project's `<workitems dir>/watch/` (the lookup tries it first); the generic ones stay in the bundled folder and get their helpers from it through `WORKITEM_MOVE`. The default board of a project may live in `<workitems dir>/boards/default.json` (read before `pipeline.json`, by the backend and `workitem-move` alike; it is not listed as a second board). The PR scripts keep everything in the workitem's own frontmatter, not in a state file (40). `bin/workitem-run-item <dir>` is how a script starts the stage handler of an item (`POST /api/workitems/{project}/{dir}/run`, the same launch as the dispatcher, refused unless the item is idle and its stage has a handler); it authenticates with `Authorization: Bearer <token>` from the config file, and the watcher gets `WORKITEM_{PROJECT,UI_PORT,UI_CONFIG}` for it. Scripts only for now; a watcher that runs an LLM prompt, and moving the built-in dispatcher and PR logic into watch scripts, are not built. Bundled: `age-out --older-than <30d> (--delete | --to <stage>)` by the `created` date; it never deletes an item with a PR link.

26. **Handler lookup chain** (built; `launch::instructions`). A handler name is a plain slug (`[a-z0-9-]+`) resolved to a `SKILL.md` in this order, first hit wins: `.workitems/boards/<board>/skills/<name>/`, then `.workitems/skills/<name>/`, then the bundled `skills/<name>/`. Claude does not discover skills in `.workitems/`, so the launcher reads the file, strips the front matter and passes the body plus the stage block (19) as the one argv prompt. A skill is therefore a prompt file, which is why `prompt_file` stays out. The bundled `workitem-start` is not copied into projects; a project overrides it by adding its own at either level.
27. **Which skills use the chain.** The stage handlers and the three the UI launches outside a stage: `create`, `start` and `remove` (bundled `workitem-create`, `workitem-start`, `workitem-remove`). For `create` the board level is the board picked in the dialog, for the others the item's own board. `workitem-approve` stays global; the gate replaces it.
33. **Stage source view** (built; `locate.rs`, `GET /api/projects/{project}/boards/{board}/stages/{stage}/source`). An info icon in every column header opens a read-only dialog with two tabs: the handler skill or inline prompt, and the watch scripts (implicit ones marked). The lookup order (board, project, bundled) lives in `locate::places` and `find`, which the dispatcher (`launch::handler_file`, `watch::resolve`) and the endpoint share, so the UI shows the file that runs. Content is fetched when the dialog opens, not in `/api/pipelines`. `builtin:` handlers have no prose tab; the PR fixer prompts are still strings in `launch.rs`. Next: editing these files through an agent, and moving those prompts into files.
34. **Pausing a column** (built; `PUT /api/projects/{project}/boards/{board}/stages/{stage}/paused` with `{"paused": bool}`). A pause button in the header of every column with a watcher stops that stage's watchers from starting: `watch::pass` skips the stage, so no script runs and, through `run-items` and `pr-review`, no handler or fixer starts and merged PRs stay put. A script that is already running finishes, agent sessions go on, manual actions and moves still work, and items moved in wait. Paused stages (`project/board/stage`) are kept in `paused.json` next to the config, not in the board file, since it is a switch, not part of the board; a renamed stage starts unpaused and its old key is ignored. Resuming only wakes the dispatcher: a watcher that came due while paused runs at once, one that did not keeps its schedule. `/api/pipelines` lists `watched` and `paused` stages per board. A column that merges several projects pauses all of them, and shows `Paused` once every one is.
35. **Follow-ups** (built; `workitem::follow_ups`). Each item carries `follow_ups`, the texts of its open follow-ups (pipeline decision 11). A card with any shows a chip "N follow-ups" in every stage, with the list as its tooltip; the detail header shows the same chip, which opens the Brief tab and scrolls to `## Follow-ups`.
36. **Planning sessions.** A planning session is a conversation about a project with no workitem and no worktree: interactive `claude --session-id <uuid>` in the repo root, tmux session `wi-plan-<id>`. It is started from the UI with one required text (what to plan), which becomes the first prompt together with the planning rules. Not `--permission-mode plan`: plan mode refuses the helper's Bash call even with an allow rule. Instead the backend passes inline `--settings` that allow the `workitem-plan-note` helper and file edits, and a `PreToolUse` hook (`bin/workitem-plan-guard`) that refuses any edit outside the workitems folder, so the session can create workitems (through the `workitem-create` skill, when asked) but never edits code. Other shell commands still ask in the terminal. The settings also carry the Notification hook and a `UserPromptSubmit` hook that sets the record back to `working`. A saved plan and a workitem are possible outcomes, not required ones; there is no "create workitem" button. Each session has a record `<workitems dir>/plans/<id>.md` with flat frontmatter (`topic`, `summary`, `status`: `working`, `waiting` or `ended`, `claude_session`, `created`, optional `workitem`) and an optional plan as its body; the record, not tmux, is the source of truth, and tmux only tells whether it is live. The agent updates it only through `bin/workitem-plan-note` (a one-line summary after each meaningful step, `--status`, `--plan` from stdin, `--workitem <dir>`), which finds the record through `WORKITEM_PLAN`; `workitem-notify` sets `waiting` when the session needs input. The record body is `## Prompt` (the full text typed in the UI) and, once saved, `## Plan`; `topic` is its first line. An exited session is killed by the dispatcher housekeeping and its record set to `ended`; **Resume** starts `claude --resume <uuid>` in a new `wi-plan-<id>` session. A record goes away only through Delete, which also kills the session. The UI shows a collapsible Plans bar above the board (replacing the agent-session strip; `wi-new-*` links stay at its end): one card per plan of the shown projects with topic, summary and status, done plans (with a `workitem`) in a collapsed group. A card opens the right panel with *Terminal* (or Resume), *Plan* (only when a plan is saved) and Delete.
37. **Learnings from reviews** (built; `launch::learnings`). Each board has its own file: `<workitems dir>/learnings.md` for the default board, `<workitems dir>/boards/<board>/learnings.md` for the others, and a board does not get the default board's rules (a review board needs other rules than development). The two review fixers (changes requested, new comments) end by writing what generalises into the item's board file: one bullet per rule, with a source link to the comment, only for a comment they acted on whose lesson applies beyond the PR and is not already in the repo's CLAUDE.md/AGENTS.md or the file. A rule that is already there gets the new source link instead of a second bullet. The launcher pastes the board's file into the prompt of `develops` stages, stages with `"learnings": true`, and all four fixers (not other stages, the brief chat or manual sessions), so it does not depend on the worktree's cwd the way Claude Code's own memory does, and it never lands in a PR diff. The header's Learnings button shows the file of the board on screen and edits it (`GET`/`PUT /api/projects/{project}/boards/{board}/learnings`); that is how rules are added by hand, pruned, or moved to CLAUDE.md. A save sends the text the editor started from and is refused if the file changed since. Fixers write with plain edits; two racing are caught by the edit tool's changed-since-read check and retried. Left for later: a review board writing its own learnings, for example from a re-check of the PR after new commits.
38. **Board watchers** (built; `watch.rs`). A board file can carry a top-level `"watch"` (one object or a list, same shape as a stage watch). It runs like a column watcher, but stdin holds every item of the board, whatever its stage (`done` included), and `WORKITEM_STAGE`, `WORKITEM_NEXT` and `WORKITEM_ON_MERGE` are empty. Its last start is kept in `watch.json` as `project/board/@board/<i>` (`@` is never in a stage name). It has no column header, so it cannot be paused and the stage source view does not show it; remove the line to stop it. The bundled default board runs the bundled `watch/issue-status` every 5m: one Jira Cloud search per 100 keys (`POST /rest/api/3/search/jql`, `key in (...)`, any project) writes `issue_status` and `issue_status_category` into items whose value changed. It reuses the jira-cli setup (`server` and `login` from its config, the token from `JIRA_API_TOKEN`, `~/.netrc` or the OS keyring, service `jira-cli`), so it works wherever `jira` does, and logs one line and exits 0 without it. A project board that replaces the bundled one needs the same line to keep the sync.
39. **Agent per project** (built; `config.rs`, `launch.rs`). A project in `config.toml` can carry `agent`, the executable that runs every session of that project: stage handlers, PR fixers, create/start and planning sessions. It is per user, not in the repo, because it is a personal choice (a wrapper like `yolo` that adds `--dangerously-skip-permissions`). It must be one executable, a name on `PATH` or an absolute path, with no whitespace: flags belong in a wrapper script, since the agent runs without a shell. It must take Claude's arguments (`--settings`, `--add-dir`, `--session-id`, `--resume`, the prompt) and fire its hooks; agents with another CLI (opencode, omp) need an adapter and are not supported yet. It is set in the UI (*Agent* next to the project filter, `PUT /api/projects/{name}` with `{"agent"}`); the save checks that the name resolves, and an empty value clears it. The launcher resolves it to an absolute path on every launch, because a tmux session gets the tmux server's `PATH`, not the backend's. Without `agent` a project uses `WORKITEM_UI_CLAUDE` (default `claude`). Switching the agent does not touch running sessions; a plan resumed afterwards resumes with the new agent.
40. **PR status as facts, reactions as a stage watcher** (built; `watch/pr-status`, `watch/pr-review`, `bin/workitem_fields.py`). Reading a PR and reacting to it are two scripts that talk only through the item's frontmatter. `watch/pr-status` (a board watcher, every 1m on the bundled board) reads the PR of every item of the board that has a PR link and is not recorded as merged (a closed one can be reopened), with `gh pr view` plus `gh api` for inline comments, and writes: `pr_url` (the link it read; a different `pr:` clears every `pr_*` key and starts over), `pr_state` (`open`, `merged`, `closed`), `pr_ci` (`passing`, `failing`, `pending`, `none`, over every check, for the chip), `pr_ci_fix` (the same without checks named after an `--ignore` word, default `dockerized,e2e,playwright`, for the CI fixer), `pr_ci_failed` (names of the red checks), `pr_merge` (`mergeable`, `conflicting`, `unknown`), `pr_approval` (`approved`, `changes_requested`, `review_required`, `none`), `pr_approved_by_me`, `pr_draft`, `pr_head`, `pr_head_at` (when it first saw that head, so a project script can wait until pushes settle; the storyrails `recheck-due` does) and `pr_unseen_comments` (ids of comments that ask for a change and are not in `pr_seen_comments`; every changes-requested review counts, as `review-<id>`; the first reading of an item puts what is already there into `pr_seen_comments`). Keys are written only when they change. `pr_checked_at` (UTC with milliseconds) is written with every change, and on every reading while `pr-review` waits for one newer than `pr_fix_ended_at`; not on every run, because Claude Code tells every agent that read the file about each write. It starts nothing. `watch/pr-review` on the PR stage (every 5s) reads only frontmatter, never `gh`, and does at most one thing per item, in this order: merged moves to `on_merge`, closed blocks, then (idle items only) a conflict fixer, a CI fixer (at most `--max-attempts` per red streak, `pr_fix_attempts`) and a comments fixer (it moves `pr_unseen_comments` into `pr_seen_comments`). It remembers the running fixer as `pr_fixing`; once the item is idle again it stamps `pr_fix_ended_at` and acts only on a `pr_checked_at` later than that, so it never reacts to a reading from before the fixer pushed. A CI or conflict fixer is tied to the head it started on (`pr_ci_head`, `pr_conflict_head`): a fresh reading with the same head still red or conflicting means the fixer pushed nothing, and the item is blocked. While an item is blocked its heads and attempts are forgotten, so clearing the block tries again. Both scripts write through `bin/workitem_fields.py`, which rereads the file right before an atomic rename and starts over when someone wrote in between, since agents, the backend and both scripts edit the same file. The chips come from the frontmatter (`review::PrStatus::from_fields`) on any item with `pr_state`, so they survive a restart and a merged PR shows as merged; `PUT/DELETE .../review` and the in-memory map are gone, and the failing checks link to the PR's checks page. The merge and rebase buttons make the board's watchers due. A board with a stage that watches PRs (or one with `pr_status: true`, 30) but no `pr-status` anywhere gets it as an implicit board watcher every 1m, and an old-style `builtin:pr-review` stage runs `pr-review` every 5s, so older boards keep their fixers. The changes-requested fixer kind is gone: the comments fixer handles reviews too, and an old `pr_handled_review` is folded into `pr_seen_comments`.

## UI

Kanban, one column per stage, project filter in the header (with add and remove project, and "New workitem").

- **Card:** title, project badge, `agent_status` chip (blocked in red with reason, working with spinner, waiting as a calm 💤 chip with the reason in its tooltip and no alert), terminal icon when a session is alive. In `in_review`: approval, merge and CI pills.
- **Detail panel** (right, on card click), tabs: *Brief* (rendered `workitem.md`; *Edit* swaps in a textarea for the body after the frontmatter, and the save is refused with 409 if the file changed since the editor opened), *Terminal* (xterm.js, can pop out to its own browser tab), *Actions* (approve/reject with comment, clear blocked, kill session, start, start agent session, remove; only those valid for the state are shown). The header has "New workitem".
- **URL and history:** the selected item and its tab live in the hash (`#<project>/<dir>[/<tab>]`). Card clicks, tab switches and Close push a history entry, Back/Forward walk them, and a pasted deep link opens the item on that tab.
- No drag-and-drop. Moves happen only through the rule-checked actions.

## Layout and build

```
ui/backend    Rust, axum
ui/frontend   React, Vite, TypeScript, xterm.js
```

One binary: the built frontend is embedded (`rust-embed`) and served with the API and WebSocket on one port. Dev: `vite dev` proxies `/api` and `/ws` to the Rust server. `install.sh` is unchanged; the UI is built with `cargo build --release`.

## Build order

1. **Read-only board and terminal.** Config and project add/remove, frontmatter reader, tmux listing, token auth, PTY bridge, kanban, detail panel, terminal. Done when you can open a blocked item and type into its agent from the browser.
2. **Direct actions.** Approve, reject, clear blocked.
3. **Agent-launching actions.** Create, start, remove.
4. **Dispatcher.** Reconcile loop, notifications. Then retire `/loop /workitem-run` for auto stages.

Configurable boards (decisions 12 to 25), each step shippable on its own:

5. **Path move.** `.workitems/` with the fallback and `workitem-migrate`.
6. **Ordered format.** Array `stages`, a `/api/pipeline` endpoint, columns rendered from it, the unknown-stage column and the invalid-file handling.
7. **Roles.** Gates, `on_merge`, `require: {issue}`, replacing the hardcoded stage names in `actions.rs`, `review.rs`, `dispatch.rs` and `workitem-move`.
8. **Several boards.** `board:` frontmatter, `boards/` lookup, `--board`, the tab switcher with badges.
9. **Handler context and lookup.** The launcher's stage block, the handler lookup chain (26, 27) with the launcher reading `SKILL.md`, and the handler skills changed to use the stage block.

## Testing

- Rust unit tests: frontmatter parser, dispatcher rules (skip blocked, attempt cap, reap dead panes, session-path check).
- Integration tests against real tmux on an isolated socket (`tmux -L wi-test`) with a stub `claude` script that sets `agent_status`. The backend takes the socket name as a parameter. No tmux mocks.
- Frontend: Vitest for state logic, one Playwright smoke test of board and terminal against the stub setup.

## Non-goals

Remote or multi-user access, drag-and-drop stage moves, Jira/Sentry polling, a `workitem-watch` port, a service installer, Tauri/Electron.

## Risks

- Run rules exist in the `workitem-run` skill and in the Rust dispatcher until the skill is retired for auto stages.
- Web and real-terminal clients attached at once make tmux size the window to the smaller one.
- The token protects against other web pages, not against other local processes that can read the config file.
