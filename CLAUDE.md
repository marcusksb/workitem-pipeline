# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Two parts live here: the workitem pipeline itself (Claude skills plus one Python script) and `ui/`, Workload, a local web UI for it (Rust backend, React frontend). Design docs: `workitem-pipeline.md` (pipeline) and `workitem-pipeline-ui.md` (UI, with the numbered decisions). Read the matching doc before changing behavior.

## Commands

Pipeline:
- `./install.sh` symlinks every `skills/*` folder into `~/.claude/skills` (a real folder is moved to `backup/` first); `./uninstall.sh` reverts it.
- `python3 -m unittest test_workitem_move` tests `skills/workitem-pipeline/bin/workitem-move`. Single test: `python3 -m unittest test_workitem_move.WorkitemMoveTest.<name>`.
- `skills/workitem-pipeline/bin/workitem-migrate` moves a repo's `.claude/workitems` to `.workitems`.

UI (run from `ui/`):
- `npm install` then `npm run dev`: `vite build --watch` plus `cargo watch` (needs `cargo install cargo-watch`) on one port, 7373. The URL with `#token=` is printed on start.
- `npm test`: `cargo test` and vitest. One Rust test: `cargo test --manifest-path backend/Cargo.toml <name>`; one file: `--test pipeline`.
- `cd frontend && npm run build && npm run e2e`: Playwright smoke test. It needs `cargo build` first (it runs `backend/target/debug/workload`) and Chromium (`npx playwright install chromium`).
- `npm run build`: release binary at `backend/target/release/workload`.
- The backend embeds `frontend/dist` at compile time (`rust-embed`), so build the frontend before `cargo build` on a fresh checkout.

## Architecture

**Pipeline.** A workitem is `<repo>/.workitems/<dir>/workitem.md` (`.claude/workitems/` if that exists and `.workitems/` does not) with flat `key: value` frontmatter. `stage:` is the source of truth. Only `skills/workitem-pipeline/bin/workitem-move` changes `stage`; it enforces `pipeline.json` (allowed transitions, `require` including `issue: linked` and `brief: complete`, and `on_enter`). Never edit `stage:` by hand or reimplement those rules. `pipeline.json` is an ordered `stages` array (the order is the column order) plus `entry`; each stage names its handler skill and whether it is `auto`. Roles are keys, not stage names: `gate` (a human approves or rejects there), `on_merge` and the `pr-review` watcher (the PR stage). The API puts `gate`, `pr_watch` and `develops` on each item, so the frontend knows no stage names. A project's own `<workitems dir>/boards/default.json` (or the older `<workitems dir>/pipeline.json`) is its `default` board and replaces the bundled one in full; more boards are `<workitems dir>/boards/<name>.json`, and an item picks one with `board: <name>` in its frontmatter (`workitem-move <item> --board <name>` is the only way to change it, and puts the item on that board's `entry`). The backend keeps the last valid file per project and board (`AppState::pipeline`) and serves them on `/api/pipelines`. `agent_status` (`working`, `ok`, `blocked: <reason>`) is how agents and humans signal each other. A handler runs as interactive `claude` in tmux session `wi-<dir>`; the session is the lock, and `hooks.json` plus `bin/workitem-notify` mark a session that waits for input as blocked.

**UI backend** (`ui/backend`, axum, lib plus thin `main.rs`). It never writes `stage:` itself. It reads workitem files directly and shells out to `workitem-move` (with the full `workitem.md` path) for every stage change. Frontmatter fields it does own (approve, clear blocked) go through `workitem::set_fields`. Skills that need an LLM (`workitem-create`, `-start`, and the stage handlers) are launched by `launch::spawn` as `wi-*` tmux sessions running `claude --settings hooks.json <prompt>`. The launcher resolves a handler name to a `SKILL.md` (`launch::instructions`: `<workitems dir>/boards/<board>/skills/`, then `<workitems dir>/skills/`, then the bundled folder) and puts its body, plus a block with the stage and the allowed next stages, in the prompt. A stage can also carry an inline `prompt` instead of a `handler`. The prompt is one argv element and never passes through a shell. Keep it that way.

- `review.rs` holds what the board shows of a PR (`PrStatus`, set through `PUT .../review`) and the PR tab's conversation. The PR watching itself is the `watch/pr-review` script: it polls the PR with `gh` on its `every`, pushes the status, moves merged PRs to the stage `on_merge` names, and starts fixer sessions (`POST .../fix`, prompts in `launch.rs`) for red CI (cap 3), conflicts, changes-requested reviews, and new comments that ask for a change. `WORKITEM_UI_GH` swaps the `gh` binary (passed to the script as `WORKITEM_GH`); tests use a stub.
- `dispatch.rs` keeps the session housekeeping of the `workitem-run` rules (notify, reap) and then runs the column watchers; it reconciles every 5s and on `state.wake`. Starting handlers is a column watcher: `watch/run-items` (attempt cap of 3 kept as `handler_attempts` in the item, which `workitem-move` clears on every stage change; `once`; `when`) decides and calls `workitem-run-item`, which asks `POST .../run` (`dispatch::run_handler`) to launch. Stages written the old way (`auto` plus a handler or prompt) get that watcher implicitly. `workitem-watch` is not used by the UI; `watch/pr-review` does its job. Do not run it together with `/loop /workitem-run`.
- `AppState.busy` serialises session launches and dispatcher passes. Take it around any check-then-launch, or an item can start twice.
- A session belongs to a project only if its `@workitem_repo` option (`#{session_path}` when unset) equals the project's repo (`tmux::session_for`), because session names carry no repo. `launch::spawn` sets it in the same tmux call that creates the session, and starts a workitem's session in its worktree when one exists (with `--add-dir <repo>`). Sessions without a workitem are `wi-new-*` (`tmux::is_agent_session`).
- `watch.rs` runs a stage's `watch` script (`every`, `command`, `args`) on a timer, whether or not the column has items; scripts live in `watch/` folders resolved like handlers (only scripts that cannot be shared between projects belong in a project's `<workitems dir>/watch/`; the generic ones stay bundled), get context in env vars and the column's items as JSON on stdin, and last start times are kept in `watch.json`. The bundled `watch/age-out` deletes or moves old items, and `watch/pull-queue` is the queue (an `auto` stage with no handler gets it implicitly, every 5s). `bin/workitem-run-item <dir>` lets a script start an item's stage handler through the backend (`/run`, Bearer token). `watch/pr-review` keeps its per-item bookkeeping in the workitem's frontmatter (`pr_*` keys). Rules belong in the scripts, not in Rust.
- `terminal.rs` runs `tmux attach-session` on a PTY (`portable-pty`) bridged to a WebSocket. Binary frames are keystrokes, text frames are `{"cols","rows"}` resizes. Closing the socket kills the attach client only; the agent session survives.
- `files.rs` backs the detail panel's Files tab: it lists the workitem folder, serves one file raw (with `Content-Security-Policy: sandbox`, because it shares the UI's origin), and reveals one in Finder (`open -R`; `xdg-open` on its folder elsewhere). It does not follow or list symlinks, and never leaves the folder.
- `auth.rs` guards everything: Host must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding), `/api` and `/ws` need the token cookie, and `/ws` also needs `Origin` equal to the Host. The token lives in `~/.config/workitem-ui/config.toml` (mode 0600), which also holds the project list.
- Behavior is tunable by env: `WORKITEM_UI_{PORT,CONFIG,TMUX_SOCKET,SKILLS,CLAUDE,GH,DISPATCH}` (see `AppState::new`). `DISPATCH=off` matters for tests and for running a second instance.

**UI frontend** (`ui/frontend`, React, Vite, xterm.js). It polls `/api/*` every 3s; there is no push channel. Pure state logic is in `boardState.ts`; it is kept apart from `Board.tsx` because the two names differ only in case and collide on macOS. Vite's dev proxy rewrites Host and Origin, since the backend rejects anything else.

## Testing approach

Backend integration tests (`ui/backend/tests`) run against a real tmux server on an isolated socket (`tmux -L`, see `tests/common`), the real `workitem-move` from `skills/`, and a stub `claude` script whose per-stage behavior comes from `<repo>/.stub-<stage>` files. Do not mock tmux. Tests must not touch the default tmux server or a real config: use `AppState::new` and override fields.
