# Decision log

History of the numbered design decisions, newest last. It is append-only: a decision is never edited or renumbered, because code comments cite them by number ("decision 61"). A later decision may supersede an earlier one; the current behaviour is in [`spec.md`](spec.md), and where the two disagree the spec wins.

A behaviour change appends the next number to the Workload UI list below and folds its result into `spec.md`.

## Workload UI decisions

Numbered 1 to 88 (57 to 59 were never used; 26 and 27 sit after 32). Code comments that say "decision N" mean this list.

1. **Access:** localhost only. Bind `127.0.0.1`, fixed port (default 7373, overridable).
2. **Auth:** persistent random token, generated on first run and stored in `~/.config/workitem-ui/config.toml` (mode `0600`). The backend prints `http://127.0.0.1:<port>/#token=…`. The page posts the fragment once to `/api/login` and gets an `HttpOnly; SameSite=Strict` cookie. Every API call and WebSocket upgrade checks the cookie; the WebSocket also requires `Origin` to equal the server's own origin. `workload --rotate-token` replaces the token.
3. **State:** the backend reads `<repo>/.claude/workitems/<dir>/workitem.md` directly. It never writes `stage:` itself. Every stage change runs `bin/workitem-move <full path to workitem.md> <stage>`, so the transition and brief rules live in one place.
4. **Projects:** listed in `config.toml` (name, repo dir). The UI can add and remove projects. Removing a project only drops it from the config.
5. **Terminal:** the backend opens a PTY (`portable-pty`) running `tmux attach -t wi-<dir>` and bridges it over a WebSocket to xterm.js. Closing the tab kills the attach client only; the session and agent keep running. The session name is built from a known workitem, never from raw input. The browser's tab shortcuts (Ctrl+Tab, Ctrl+Shift+Tab, Ctrl+PageUp/PageDown) skip xterm, which would otherwise send them to the agent and cancel them; Shift+PageUp/PageDown scrolls the terminal history.
6. **Live data:** the browser polls `GET /api/state` every 3s (decision 78). The backend re-reads frontmatter and runs `tmux list-sessions` per call; only board files are cached, by modification time. No push.
7. **Session naming:** keep `wi-<dir>`. A session belongs to a project when its `@workitem_repo` option (set by the launcher in the same tmux call that creates it; `#{session_path}` for sessions without it) equals the project's repo dir. A workitem's session starts in its worktree (`<workspace>/.worktrees/<repo-name>-<dir>`, decision 80) when git has one, with `claude --add-dir <repo>` so the agent can still edit `workitem.md`; otherwise in the repo. The UI refuses to start a session if `wi-<dir>` already exists and names the conflicting repo.
8. **Actions.**
   - Direct in the backend: approve (`approved: true`, `approved_at`), reject with comment (back to `analyze`), clear blocked, kill session. Deterministic, no tokens. Clear blocked sets `working` when the session is still alive (the agent waits for its answer; `ok` would make the dispatcher kill it) and `ok` otherwise. Kill session ends the session and sets `ok`, so the dispatcher retries or stops at the attempt cap.
   - Through tmux agents, same pattern as `workitem-run` step 4 (`claude --settings …/hooks.json "<prompt>"`, `remain-on-exit on`):
     - start: `wi-<dir>` running `workitem-start`
     - discuss brief: `wi-<dir>` with a prompt that opens on the brief and plan, in any stage. The human talks it through; the agent edits the brief only on request and never touches `stage:` or `approved:`
     - create: `wi-new-<id>` running `workitem-create` (input: Jira key, Sentry URL or text)
     - remove: no agent. The backend stops the item's `wi-<dir>` session (this project's only), runs `bin/teardown_worktree` if the worktree has one, `git worktree remove` (never `--force`; if git refuses the worktree is left and reported), then deletes the folder, all before the request returns, so the dispatcher never sees a half-removed item. Works in every stage. Branch and PR stay. A final column (a stage whose `next` is empty on every project in view, e.g. `done`) has a "Clear" button in its header. It opens a dialog that picks which items to remove: only those without open follow-ups (the default, so items with work left stay) or all of them. It runs this remove for each, one after another, and lists any that failed.
   - User-typed text goes to `claude` as an argv element, never through a shell string. `<dir>` is validated against known workitems.
9. **Dispatcher** (the handler start and the PR rules below now live in the `run-items` and `pr-review` watch scripts, see 32; `dispatch.json` is no longer written, and the attempt counts are item frontmatter): a Rust reconcile loop owns `backlog`, `analyze` and `in_development` (`workitem-start` gets the start prompt, since it writes code). It applies `workitem-run` steps 1 to 4: reap finished sessions, skip `blocked` items, cap attempts at 3 then set `blocked: max attempts reached in stage <stage>`, start `wi-<dir>` with the handler prompt. State file `dispatch.json` next to the config (the skill's file lives in a Claude session scratchpad, which the backend cannot see). It reconciles every 5s and immediately after any UI action, so a new item, a stage change or an ended session is picked up within seconds. A pass reads a few small files and one `tmux list-sessions`, so it costs no tokens when idle. Idle passes cost no tokens. An approved item in `ready_for_development` is started right away with the `in_development` handler (approving wakes the loop). `in_review` (`workitem-watch`) is not dispatched as a skill; the dispatcher owns the PR status and four fixers (`review.rs`): at most once a minute per item it runs `gh pr view <pr url>` (no tokens) and keeps approval, merge and CI status in memory for the board's chips. A merged PR moves the item to `done`; a closed one blocks it. Red CI (once every check other than `dockerized|e2e|playwright` has settled) starts a fixer session `wi-<dir>` that fixes, pushes and sets `ok`, or sets `blocked: <reason>` and waits for the human in the session. Attempts cap at 3 per red streak, then `blocked: CI still failing after 3 fix attempts`; green CI resets the count. A merge conflict starts a `wi-<dir>` session that rebases onto the base branch, resolves only obvious conflicts, and force-pushes with lease after tests and lint pass; otherwise it sets `blocked` and waits. It runs once per PR head sha (`conflict_head` in `dispatch.json`), so a fixer that gave up is not retried until someone pushes. A `CHANGES_REQUESTED` review starts a fixer once per review id (`handled_review`); in one pass, CI goes first, then the conflict, then the review. Neither has an attempt cap, since one head or one review starts one fixer. Comments that ask for a change are last in the pass: inline comments from others, `COMMENTED` reviews from others that have a body (ids `review-<id>`), every PR comment from others (bots included, since review bots such as Quality Risk Review post their findings as one), and the reader's own comments with `@change` or as a new inline thread (not a reply). Detection is one `gh api` call for the inline ones (the PR comments come with the poll) and only runs while the item is idle. A batch of new ones starts one `wi-<dir>` fixer; `comment_mark` in `dispatch.json` is the creation time of the newest one handled, and the first reading of an item only sets it, so comments already on a PR are not new. `/loop /workitem-watch` would fix all of these too, so do not run it beside the UI. `/loop /workitem-run` is turned off for auto stages once this ships; two runners would race.
10. **Notifications:** the frontend fires a browser notification and a beep when polling shows an item newly `blocked`. It needs an open tab and one click per page load for sound and permission. The item open in the detail panel gets neither while the page has focus (its question is on screen); unfocused, it alerts as any other.
11. **Lifecycle:** no service. You start the backend from your shell; the dispatcher runs while it runs. State is on disk and tmux outlives the backend, so a restart re-reconciles.

Sessions without a workitem (`wi-new-*`) show as toasts with a pop-out terminal link (decision 75), because a blocked create session can only be answered by attaching. Env overrides: `WORKITEM_UI_PORT`, `WORKITEM_UI_CONFIG`, `WORKITEM_UI_TMUX_SOCKET`, `WORKITEM_UI_SKILLS` (default `~/.claude/skills`), `WORKITEM_UI_CLAUDE` (default `claude`), `WORKITEM_UI_GH` (default `gh`), `WORKITEM_UI_DISPATCH=off`.

### Configurable boards (planned)

Each project can define its own boards: the columns, and what each column's watcher does. Decisions 12 to 27 extend the list above. Once built they replace the hardcoded paths and stage names in decisions 3, 8 and 9. The file format was in the pipeline design doc; it is now in `spec.md`.

12. **Location.** Items and config live in `<repo>/.workitems/`, not under `.claude/`, so the pipeline is not tied to Claude. If `.workitems/` does not exist, `<repo>/.claude/workitems/` is read instead, so existing projects keep working. `workitem-migrate` moves an old folder over; nothing migrates by itself. The path is built in one place per language (`workitem-move`, `workitem.rs`).
13. **Scope.** Boards are per project and configured by file only; there is no editor in the UI (except the top-level settings, 73). A project's board file replaces the bundled `skills/workitem-pipeline/pipeline.json` in full, with no merging. A project without a file uses the bundled one.
14. **Format.** `stages` is an ordered array and its order is the column order. `label` is optional and defaults to the name with `_` shown as a space.
15. **Handlers** (a stage with a `prompt` and no `handler` is dispatched like a skill stage). A stage has one of: a skill name (`handler`), `handler: "builtin:pr-review"`, an inline `prompt` string, or neither (a manual column). Having both `handler` and `prompt` is invalid. `prompt` is a plain string, started like a skill (same tmux session, attempt cap and `ok`/`blocked` handling, argv element, no shell); anything long should be a skill. Shell commands and `prompt_file` are out.
16. **Roles, not names.** The backend, UI and `workitem-move` no longer know stage names. A closed set of keys carries the roles: top-level `entry` (where new items start); `gate` (below); `on_merge` (on the `builtin:pr-review` column, the stage a merged PR moves to); `require` (`issue: "linked"` and `brief: "complete"` are checks, replacing the Jira and Review brief rules hardcoded for `ready_for_development`; any other key compares a frontmatter value, as before). `next`, `auto` and `on_enter` keep their meaning.
17. **Gates.** `gate: {label, approve_to, reject_to}` is a column where a human decides. The button shows `label`. Approving sets `approved: true` and `approved_at`, then moves the item to `approve_to` with `workitem-move` (a refused move puts `approved` back to false); rejecting (with a comment) moves it to `reject_to`. Both targets must be in the stage's `next`. A board can have any number of gates. There is no separate start stage: the dispatcher runs the handler of whatever stage `approve_to` names, so the `in_development` hardcode in `dispatch.rs` is gone. A gate gives items without a PR a way to reach the end, for example "Implementation approved" with `approve_to` the last stage. The "Start development" action is offered for an approved item whose stage has the handler `workitem-start`.
18. **PR watcher.** The handler `builtin:pr-review` is the existing `review.rs` (poll, chips, fixers, merge). At most one per board, and it needs `on_merge` (the stage a merged PR moves to, in the stage's `next`), which no other stage may have. Builtin handlers are never started as sessions. The PR chips and PR actions show on that column, whatever it is called. The API tells the UI what a stage allows (`gate`, `pr_watch`, `develops` on each item), so the UI knows no stage names. An `on_commit` watcher is out for now and can be added later as another builtin.
19. **Handler context** (built; `launch::stage_context`). The launcher adds a block to every handler prompt, skill or inline: the workitem path, the current stage, and the allowed `next` stages (the first is the default forward move). Handler skills move to "the default next stage" or the stage the prompt names instead of naming stages themselves. `workitem-move` still enforces every rule.
20. **Mismatches.** An item whose stage is not on its board shows in an extra "unknown stage" column at the right end, flagged, and the dispatcher skips it; `workitem-move` can still move it, but only to the board's `entry`. An invalid board file (bad JSON, a `next` or role pointing at a missing stage, no `entry`, both `handler` and `prompt`, two `builtin:pr-review`) is rejected as a whole: the last good config stays in use, the board shows an error banner and the reason is logged. The dispatcher never runs on a half-valid file. `workitem-move` refuses the same files, so a move never follows rules the dispatcher rejected: both test suites read `testdata/boards/`, where every file but `valid.json` (the base each fixture changes in one place) must be rejected by `Pipeline::parse` and by `workitem-move`, and `rust-only/` holds the rules only the backend checks because no move depends on them (model, order, label, reviewers, watchers, handler with prompt, the PR stage). A new board rule gets a fixture in the matching folder. A missing file falls back to the bundled one.
21. **Several boards per project.** `.workitems/pipeline.json` is the `default` board; further boards are `.workitems/boards/<name>.json`, and the board id is the file name. Items stay flat in `.workitems/<dir>/`; an item picks its board with `board: <name>` in its frontmatter, and a missing key means `default`. `workitem-move`, `workitem.rs` and the dispatcher load the board named by the item. `next` only names stages of the same board.
22. **Creating and switching.** `workitem-create` takes a board (default `default`); the UI's create dialog pre-selects the board on screen, and the item starts at that board's `entry`. `workitem-move <path> --board <name>` is the only way to change `board:`: it lands on the target's `entry` (running its `on_enter`), resets the attempt counter like any stage change, and is refused while the item has a live session. There is no stage mapping between boards. The command line is the only way to switch for now; the detail panel has no button for it. `/api/pipelines` lists each project's boards (`default` first, then by name), and `POST /api/projects/<p>/create` takes an optional `board` that must be one of them.
23. **Board tabs.** The UI shows one board at a time, with a tab per board (hidden when a project has one board). Each tab carries a badge with its number of blocked items. The selected board is part of the hash, as `?board=<name>` after the item path (`#app/x-1/pr?board=research`, or `#?board=research` with no item). An unknown or missing board in the hash shows the first tab. An item whose `board:` has no file goes into an "unknown board" bucket on `default`, so it never disappears: it is shown in the unknown-stage column, whatever its stage is called.
24. **Approval per gate.** Entering a gate clears `approved` (`on_enter`), and approving sets it and moves the item. A later stage that needs the flag asks for it with `require: {approved: "true"}`; nothing relies on one flag staying set across the board.
25. **Left out for now.** An in-UI board editor (73 edits only the top-level settings), `on_commit` or other new builtins, `prompt_file`, shell-command handlers, partial overrides of the bundled file, automatic stage mapping between boards.

28. **Limits and queues.** `limit` on a stage is enforced by `workitem-move` (it counts the other items of the same board in that stage) and by nothing else, so a manual move and the dispatcher meet the same rule. A stage that is `auto` with no `handler` and no `prompt` is a queue: it is watched by the bundled `watch/pull-queue` script (written into the stage as a `watch` every 5s when the file does not name one): it moves the stage's idle items (`ok`, no session) to `next[0]` through `workitem-move`, ordered by `created` and then by directory name, and stops at the first refusal. A board can name its own watch (a different `every`, or its own script) on such a stage.
29. **`once` and `when`.** A handler stage with `once: true` starts at most once per entry (the attempt counter, which a stage change resets, is the memory), so a stage with `next: []` does not restart its handler every pass. `when` is a map of frontmatter values that must all match before the handler starts, for example `approved: "true"` on a stage that a gate's reject also leads to.
30. **`pr_status`** (superseded by 40: the key now only makes the board read its PRs). A stage with `pr_status: true` gets the PR chips on its cards without being the `builtin:pr-review` stage, which also starts fixers and merges. After each pass `review::refresh_due` reads the PR of idle-or-not items in such stages with `gh pr view`, at most 5 per pass and each at most every 5 minutes (five times the PR stage's interval), and keeps the result in the same map the API reads. Merged or closed PRs drop their chips. For reviewing other people's PRs.
31. **PR review board** (a project's own board, plan in `pr-review-board-plan.md`). The queue, the limit and a gate whose approve and reject both lead to the final stage are built from the keys above; the intake of PRs is a skill run on a loop, outside the backend, so Jira/Sentry/PR polling stays a non-goal of the backend itself.
32. **Column watchers** (built; `watch.rs`). A stage can carry `"watch": {"every": "1d", "command": "age-out", "args": ["--older-than", "30d", "--delete"]}`: a script the dispatcher starts when `every` (`30s`, `10m`, `2h`, `1d`) has passed since its last start, whether or not the column has items. The rules live in the script, not in the backend: moving, deleting or creating items is the script's job, through `workitem-move` and the workitem files. The script is a file found in `<workitems dir>/boards/<board>/watch/`, then `<workitems dir>/watch/`, then the bundled `watch/`, and is run directly, never through a shell. It gets `WORKITEM_{REPO,DIR_ROOT,BOARD,STAGE,NEXT,MOVE}` in the environment and the column's items as a JSON array on stdin, runs in a task of its own (one at a time per watcher, killed after 10 minutes) and costs no tokens. Last start times are in `watch.json` next to the config, so a restart does not rerun a daily script. The dispatcher's "start the handler" half is the bundled `watch/run-items` (`auto` stages with a handler or prompt get it implicitly, every 5s): it skips items that are not `ok`, have a session, or miss the stage's `when`, honors `once`, counts attempts per stage entry in the item's frontmatter (`handler_attempts`, which `workitem-move` drops on every stage change) and sets `blocked: max attempts reached in stage <stage>` after 3 (`--max-attempts`) or `blocked: <reason>` when `workitem-run-item` exits 2 (handler not found). Reaping finished or crashed sessions stays in `dispatch.rs`. Only scripts that cannot be shared between projects belong in a project's `<workitems dir>/watch/` (the lookup tries it first); the generic ones stay in the bundled folder and get their helpers from it through `WORKITEM_MOVE`. The default board of a project may live in `<workitems dir>/boards/default.json` (read before `pipeline.json`, by the backend and `workitem-move` alike; it is not listed as a second board). The PR scripts keep everything in the workitem's own frontmatter, not in a state file (40). `bin/workitem-run-item <dir>` is how a script starts the stage handler of an item (`POST /api/workitems/{project}/{dir}/run`, the same launch as the dispatcher, refused unless the item is idle and its stage has a handler); it authenticates with `Authorization: Bearer <token>` from the config file, and the watcher gets `WORKITEM_{PROJECT,UI_PORT,UI_CONFIG}` for it. Scripts only for now; a watcher that runs an LLM prompt, and moving the built-in dispatcher and PR logic into watch scripts, are not built. Bundled: `age-out --older-than <30d> (--delete | --to <stage>)` by the `created` date; it never deletes an item with a PR link.

26. **Handler lookup chain** (built; `launch::instructions`). A handler name is a plain slug (`[a-z0-9-]+`) resolved to a `SKILL.md` in this order, first hit wins: `.workitems/boards/<board>/skills/<name>/`, then `.workitems/skills/<name>/`, then the bundled `skills/<name>/`. Claude does not discover skills in `.workitems/`, so the launcher reads the file, strips the front matter and passes the body plus the stage block (19) as the one argv prompt. A skill is therefore a prompt file, which is why `prompt_file` stays out. The bundled `workitem-start` is not copied into projects; a project overrides it by adding its own at either level.
27. **Which skills use the chain.** The stage handlers and the three the UI launches outside a stage: `create`, `start` and `remove` (bundled `workitem-create`, `workitem-start`, `workitem-remove`). For `create` the board level is the board picked in the dialog, for the others the item's own board. `workitem-approve` stays global; the gate replaces it.
33. **Stage source view** (built; `locate.rs`, `GET /api/projects/{project}/boards/{board}/stages/{stage}/source`). An info icon in every column header opens a read-only dialog with two tabs: the handler skill or inline prompt, and the watch scripts (implicit ones marked). The lookup order (board, project, bundled) lives in `locate::places` and `find`, which the dispatcher (`launch::handler_file`, `watch::resolve`) and the endpoint share, so the UI shows the file that runs. Content is fetched when the dialog opens, not in `/api/pipelines`. `builtin:` handlers have no prose of their own. The PR fixers' steps are bundled skills (`workitem-fix-ci`, `workitem-fix-comments`, `workitem-fix-conflict`), resolved with the same lookup (`launch::Fixer`, `launch::instructions`), so a board or workspace overrides them like any handler; the launcher wraps them with what happened to which PR, the worktree, the workitem file, the board's learnings (and for comments, where to record new ones). The PR stage's prose tab lists the three. A fixer whose skill is missing answers 422, like a missing handler. Next: editing these files through an agent.
34. **Pausing a column** (built; `PUT /api/projects/{project}/boards/{board}/stages/{stage}/paused` with `{"paused": bool}`). A pause button in the header of every column with a watcher stops that stage's watchers from starting: `watch::pass` skips the stage, so no script runs and, through `run-items` and `pr-review`, no handler or fixer starts and merged PRs stay put. A script that is already running finishes, agent sessions go on, manual actions and moves still work, and items moved in wait. Paused stages (`project/board/stage`) are kept in `paused.json` next to the config, not in the board file, since it is a switch, not part of the board; a renamed stage starts unpaused and its old key is ignored. Resuming only wakes the dispatcher: a watcher that came due while paused runs at once, one that did not keeps its schedule. `/api/pipelines` lists `watched` and `paused` stages per board. A column that merges several projects pauses all of them, and shows `Paused` once every one is.
35. **Follow-ups** (built; `workitem::follow_ups`). Each item carries `follow_ups`, the texts of its open follow-ups (pipeline decision 11). A card with any shows a chip "N follow-ups" in every stage, with the list as its tooltip; the detail header shows the same chip, which opens the Brief tab and scrolls to `## Follow-ups`.
36. **Planning sessions.** A planning session is a conversation about a project with no workitem and no worktree: interactive `claude --session-id <uuid>` in the repo root, tmux session `wi-plan-<id>`. It is started from the UI with one required text (what to plan), which becomes the first prompt together with the planning rules. Not `--permission-mode plan`: plan mode refuses the helper's Bash call even with an allow rule. Instead the backend passes inline `--settings` that allow the `workitem-plan-note` helper and file edits, and a `PreToolUse` hook (`bin/workitem-plan-guard`) that refuses any edit outside the workitems folder, so the session can create workitems (through the `workitem-create` skill, when asked) but never edits code. Other shell commands still ask in the terminal. The settings also carry the Notification hook and `UserPromptSubmit` and `PostToolUse` hooks that set the record back to `working` (a permission prompt the user approved submits nothing). A saved plan and a workitem are possible outcomes, not required ones; there is no "create workitem" button. Each session has a record `<workitems dir>/plans/<id>.md` with flat frontmatter (`topic`, `summary`, `status`: `working`, `waiting` or `ended`, `claude_session`, `created`, optional `workitem`) and an optional plan as its body; the record, not tmux, is the source of truth, and tmux only tells whether it is live. The agent updates it only through `bin/workitem-plan-note` (a one-line summary after each meaningful step, `--status`, `--plan` from stdin, `--workitem <dir>`), which finds the record through `WORKITEM_PLAN`; `workitem-notify` sets `waiting` when the session needs input. The record body is `## Prompt` (the full text typed in the UI) and, once saved, `## Plan`; `topic` is its first line. An exited session is killed by the dispatcher housekeeping and its record set to `ended`; **Resume** starts `claude --resume <uuid>` in a new `wi-plan-<id>` session. A record goes away only through Delete, which also kills the session. The UI lists plans in a collapsible Plans section of the sidebar (replacing the agent-session strip; `wi-new-*` sessions are toasts, decision 75): one row per plan of the shown workspace with its status and topic (the summary is the row's tooltip), done plans (with a `workitem`) in a collapsed group. A row opens the right panel with *Terminal* (or Resume), *Plan* (only when a plan is saved), *Workitems* (the items made from it that still exist) and Delete.
37. **Learnings from reviews** (built; `launch::learnings`). Each board has its own file: `<workitems dir>/learnings.md` for the default board, `<workitems dir>/boards/<board>/learnings.md` for the others, and a board does not get the default board's rules (a review board needs other rules than development). The two review fixers (changes requested, new comments) end by writing what generalises into the item's board file: one bullet per rule, with a source link to the comment, only for a comment they acted on whose lesson applies beyond the PR and is not already in the repo's CLAUDE.md/AGENTS.md or the file. A rule that is already there gets the new source link instead of a second bullet. The launcher pastes the board's file into the prompt of `develops` stages, stages with `"learnings": true`, and all four fixers (not other stages, the brief chat or manual sessions), so it does not depend on the worktree's cwd the way Claude Code's own memory does, and it never lands in a PR diff. The prompt leaves out each rule's trailing `(source: ...)` links; the file keeps them. The Learnings button in the board tab bar shows the file of the board on screen and edits it (`GET`/`PUT /api/workspaces/{workspace}/boards/{board}/learnings`); it is hidden while a search shows several workspaces; that is how rules are added by hand, pruned, or moved to CLAUDE.md. A save sends the text the editor started from and is refused if the file changed since. Fixers write with plain edits; two racing are caught by the edit tool's changed-since-read check and retried. Left for later: a review board writing its own learnings, for example from a re-check of the PR after new commits.
38. **Board watchers** (built; `watch.rs`). A board file can carry a top-level `"watch"` (one object or a list, same shape as a stage watch). It runs like a column watcher, but stdin holds every item of the board, whatever its stage (`done` included), and `WORKITEM_STAGE`, `WORKITEM_NEXT` and `WORKITEM_ON_MERGE` are empty. Its last start is kept in `watch.json` as `project/board/@board/<i>` (`@` is never in a stage name). It has no column header, so it cannot be paused and the stage source view does not show it; remove the line to stop it. `watch/issue-status` (a workspace watcher since 55; it used to sit on the bundled board) syncs the Jira status every 5m: one Jira Cloud search per 100 keys (`POST /rest/api/3/search/jql`, `key in (...)`, any project) writes `issue_status` and `issue_status_category` into items whose value changed. It reuses the jira-cli setup (`server` and `login` from its config, the token from `JIRA_API_TOKEN`, `~/.netrc` or the OS keyring, service `jira-cli`), so it works wherever `jira` does, and logs one line and exits 0 without it. A workspace lists it in its `workspace.toml` to get the sync.
39. **Agent per project** (built; `config.rs`, `launch.rs`). A project in `config.toml` can carry `agent`, the executable that runs every session of that project: stage handlers, PR fixers, create/start and planning sessions. It is per user, not in the repo, because it is a personal choice (a wrapper like `yolo` that adds `--dangerously-skip-permissions`). It must be one executable, a name on `PATH` or an absolute path, with no whitespace: flags belong in a wrapper script, since the agent runs without a shell. It must take Claude's arguments (`--settings`, `--add-dir`, `--session-id`, `--resume`, the prompt) and fire its hooks; agents with another CLI (opencode, omp) need an adapter and are not supported yet. It is set in the UI (*Agent* next to the project filter, `PUT /api/projects/{name}` with `{"agent"}`); the save checks that the name resolves, and an empty value clears it. The launcher resolves it to an absolute path on every launch, because a tmux session gets the tmux server's `PATH`, not the backend's. Without `agent` a project uses `WORKITEM_UI_CLAUDE` (default `claude`). Switching the agent does not touch running sessions; a plan resumed afterwards resumes with the new agent.
40. **PR status as facts, reactions as a stage watcher** (built; `watch/pr-status`, `watch/pr-review`, `bin/workitem_fields.py`). Reading a PR and reacting to it are two scripts that talk only through the item's frontmatter. `watch/pr-status` (a workspace watcher since 55, every 1m) reads the PR of every item of the workspace that has a PR link and is not recorded as merged (a closed one can be reopened), with `gh pr view` plus `gh api` for inline comments, and writes: `pr_url` (the link it read; a different `pr:` clears every `pr_*` key and starts over), `pr_state` (`open`, `merged`, `closed`), `pr_ci` (`passing`, `failing`, `pending`, `none`, over every check, for the chip), `pr_ci_fix` (the same without checks named after an `--ignore` word, default `dockerized,e2e,playwright`, for the CI fixer), `pr_ci_failed` (names of the red checks), `pr_merge` (`mergeable`, `conflicting`, `unknown`), `pr_approval` (`approved`, `changes_requested`, `review_required`, `none`), `pr_approved_by_me`, `pr_draft`, `pr_head`, `pr_head_at` (when it first saw that head, so a project script can wait until pushes settle; the storyrails `recheck-due` does) and `pr_unseen_comments` (ids of comments that ask for a change and are not in `pr_seen_comments`; every changes-requested review counts, as `review-<id>`; the first reading of an item puts what is already there into `pr_seen_comments`). Keys are written only when they change. `pr_checked_at` (UTC with milliseconds) is written with every change, and on every reading while `pr-review` waits for one newer than `pr_fix_ended_at`; not on every run, because Claude Code tells every agent that read the file about each write. It starts nothing. `watch/pr-review` on the PR stage (every 5s) reads only frontmatter, never `gh`, and does at most one thing per item, in this order: merged moves to `on_merge`, closed blocks, then (idle items only) a conflict fixer, a CI fixer (at most `--max-attempts` per red streak, `pr_fix_attempts`) and a comments fixer (it moves `pr_unseen_comments` into `pr_seen_comments`). It remembers the running fixer as `pr_fixing`; once the item is idle again it stamps `pr_fix_ended_at` and acts only on a `pr_checked_at` later than that, so it never reacts to a reading from before the fixer pushed. A CI or conflict fixer is tied to the head it started on (`pr_ci_head`, `pr_conflict_head`): a fresh reading with the same head still red or conflicting means the fixer pushed nothing, and the item is blocked. While an item is blocked its heads and attempts are forgotten, so clearing the block tries again. Both scripts write through `bin/workitem_fields.py`, which rereads the file right before an atomic rename and starts over when someone wrote in between, since agents, the backend and both scripts edit the same file. The chips come from the frontmatter (`review::PrStatus::from_fields`) on any item with `pr_state`, so they survive a restart and a merged PR shows as merged; `PUT/DELETE .../review` and the in-memory map are gone, and the failing checks link to the PR's checks page. The merge and rebase buttons make the workspace's `pr-status` and the stage's watchers due. A workspace with a board that has a stage that watches PRs (or one with `pr_status: true`, 30) but no `pr-status` in its `workspace.toml` gets it as an implicit workspace watcher every 1m (55), and an old-style `builtin:pr-review` stage runs `pr-review` every 5s, so older boards keep their fixers. The changes-requested fixer kind is gone: the comments fixer handles reviews too, and an old `pr_handled_review` is folded into `pr_seen_comments`.
41. **Re-review reminders as an opt-in PR stage watcher** (built; `watch/pr-remind`). A board that wants it adds `{"every": "15m", "command": "pr-remind"}` to its PR stage; the bundled board does not, since it posts on GitHub. `pr-status` writes two more facts for it: `pr_ci_required` (the same values as `pr_ci`, over `gh pr checks --required`) and `pr_activity_at` (the latest of PR opened, last commit, human review, human comment, from one GraphQL call, because only GraphQL says which authors are bots: `gh pr view` shows `vercel`, not `vercel[bot]`; comments carrying `<!-- pr-remind -->` do not count). `pr-remind` reads only frontmatter to decide: open, not draft, mergeable, required CI passing, not approved, 2 business days (Mon-Fri) since `pr_activity_at`, `pr_reminded_at` missing or older than it, and now Mon-Fri 09:00-17:00 local. Then one GraphQL call finds who to mention (requested people, then earlier reviewers who commented or requested changes, the latter marked "re-review after your feedback"; requested teams only when that is nobody), it posts a marked PR comment and sets `pr_reminded_at`. One reminder per quiet period: the reminder itself is not activity. With nobody to mention it blocks the item (the board's alert) instead. A failed post leaves `pr_reminded_at` alone, so the next run tries again. `--dry-run` prints what it would do and why the other items are skipped.
42. **Column order per board** (built; `Pipeline::order`, `boardState::treeOrder`). A board file can carry a top-level `"order"`: a list of item fields, each optionally followed by `asc` (the default) or `desc`, e.g. `["issue_status_category", "issue_status desc"]`. Every column of the board sorts its siblings by those fields in turn and then by title; children still follow their parent. A stage can carry its own `order` of the same shape, which replaces the board's for that column. `issue_status_category` ranks `new`, `indeterminate`, `done`; other fields compare as text, numbers as numbers. Items with an empty value go last in either direction. The backend rejects a field outside `issue_status_category`, `issue_status`, `issue`, `title`, `kind`, `agent_status`, `created`, `dir`, so a typo shows as a board error instead of a silent no-op. With several projects on one board, the first project whose file has a stage `order` decides, else the first with a board `order`. No `order` means title only; the bundled board sorts by `issue_status_category`, then title.
43. **Activity toasts** (built; `activity.ts`, `ActivityToasts.tsx`, `quips.ts`). The frontend compares each poll of the items (`/api/state`) with the one before (`activityEvents`) and shows a toast, for every project and board, only for what needs you or is worth celebrating: an item done (a final stage, with confetti), a PR became approved, or an item became blocked (once per reason). Moves, CI, merges, Jira status and the rest used to toast too and were dropped as noise; the board shows them. The first poll and a PR's first reading stay quiet. Nothing is stored and the backend knows nothing of it, so it only sees what changes while a tab is open and cannot tell who made a change; a persistent log would need the writers to append events, which is a separate decision. Toasts sit bottom left of the board area, clear of the detail panel, newest on top, at most 4 with "+N more"; a poll with more than 4 events becomes one summary toast. Each leaves when its 6s countdown bar ends (paused while the stack is hovered); blocked ones stay until dismissed. Clicking one opens the item. The item open in the detail panel gets no blocked toast while the page has focus. Text is a plain line plus a random quip from `quips.ts`; each event type has its own icon animation, CSS only, and `prefers-reduced-motion` turns them into fades. There is no mute switch. Sounds and browser notifications stay in `useAlerts`.

### Workspaces

Decisions 44 to 53 replace projects with workspaces, so a feature that spans a frontend and a backend repo is handled in one place. Where an earlier decision says "project" or `<repo>/.workitems`, read "workspace" and the workspace folder; 2, 4, 7, 12, 21, 22, 23, 39 and the default-board parts of 13, 20, 32 and 37 are superseded as described here.

44. **Workspaces live in one local root** (`config.rs`). The root is `~/.workitems-pipeline/` (`WORKITEM_UI_HOME` overrides it; tests point it at a temp dir). It holds `config.toml` (token and port, mode `0600`), `paused.json`, `watch.json` and `workspaces/<name>/`. A workspace is any folder in `workspaces/` whose name matches `[A-Za-z0-9_-]+`; the folder name is the workspace name, so there is no list to keep. The UI creates one with `mkdir` and has no rename or delete. A workspace is personal: it is not shared through git, and repo paths in it are absolute. Its folder is a workitems folder: items flat in `<dir>/workitem.md`, `boards/<board>.json`, `boards/<board>/{skills,watch,learnings.md}`, `skills/`, `watch/`, `plans/`, plus an optional `workspace.toml` with `agent` (39, now per workspace only). On first start the token and port are copied from `~/.config/workitem-ui/config.toml` when it exists; its `projects` are not read, they are migrated (53).
45. **A board belongs to one repo** (`pipeline.rs`, `workitem-move`). Every board file carries `"repo"` (unless it changes no code, 54): an absolute path (`~/` is expanded) to an existing directory, or the board is invalid (20). An item's repo is always its board's repo; items never store one. Several boards may name the same repo (a development board and a PR review board). There is no `default` board, no `pipeline.json` and no fallback to the bundled file: every item carries `board: <name>`, and `workitem-move` refuses an item without one or whose board has no file. Such items show in the unknown-stage column of the workspace's first board, so they never disappear. The bundled `pipeline.json` is a template only: *Add board* in the UI asks for a name and a repo and writes `boards/<name>.json` as a copy of it with `repo` set. Every board keeps its learnings in `boards/<board>/learnings.md`. An optional `"label"` titles the board's tab ("Storyrails - Develop"); the name stays the file name and the value of `board:`, so a label can change without touching any item. Changing a board's `repo` is a file edit; do it only while none of its items has a worktree or a session.
46. **Sessions** (`launch.rs`, `tmux.rs`). A session is tagged with its workspace folder in `@workitem_workspace` (replacing `@workitem_repo`), in the same tmux call that creates it, and belongs to the workspace whose folder that is. A workitem's session gets `WORKITEM` (the dir), `WORKITEM_FILE` (absolute path of `workitem.md`), `WORKITEM_WORKSPACE` (the workspace folder), `WORKITEM_REPO` (its board's repo) and `WORKITEM_WORKTREE` (where its worktree is or goes, 80); it starts in the item's worktree when git has one, else in the repo, and always gets `--add-dir <workspace folder>` (plus `--add-dir <repo>` in a worktree), since `workitem.md` is outside the repo now. Sessions without a workitem (`wi-new-*` create sessions and `wi-plan-*`) start in the workspace folder with `--add-dir` for every board's repo. Because they start outside every repo, they get `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`, so Claude Code reads the repos' `CLAUDE.md` (and `.claude/rules`) from the added folders; repo settings, `.mcp.json` and project memory still come only from the start folder. Session names stay `wi-<dir>` and are global: the launcher refuses a name that a session of another workspace holds. Watchers get `WORKITEM_WORKSPACE` (the name) instead of `WORKITEM_PROJECT`, `WORKITEM_DIR_ROOT` (the workspace folder) and `WORKITEM_REPO` (the board's repo), and run in the repo.
47. **Dependencies between items** (`workitem-move`). `depends_on: <dir>, <dir>` in the frontmatter names items of the same workspace, on any board. A stage with `"require": {"depends_on": "merged"}` refuses entry until every one of them is merged: its `pr_state` is `merged`, or it sits in the stage its board's `on_merge` names. A dependency whose folder is gone counts as merged, since the done column's Clear removes merged items. `watch/run-items` and `watch/pull-queue` already stop at a refused move, so such items wait instead of using up attempts. `"require": {"children": "merged"}` is the same check over the items whose `parent:` is this one, and refuses an item that has none, so a parent cannot pass before its children exist. The card shows one `depends on <N>` badge with the number of open dependencies; it opens the detail panel's Depends on tab, which lists each dependency (board, stage, merged or not, a blocked one's reason) and edits the list with a picker over the workspace's items (`POST .../frontmatter`). The Children tab lists the items whose `parent:` is this one, blocked ones first, with a way into each one's session.
48. **Creating linked items** (`workitem-create`). `workitem-create` takes `--workspace <folder>` and `--board <name>` and gets the workspace's boards and their repos. When a task clearly touches several repos it creates one item per board (`<key>-api`, `<key>-ui`, ...), sets `depends_on` in the order it infers, and links the same Jira issue to each. Only the item that no other item depends on (the last of the chain) moves the Jira ticket; the others leave Jira alone.
49. **Planning sessions in the workspace** (36, `plans.rs`). A plan session starts in the workspace folder with `--add-dir` for every board's repo, so it reads all of them. `workitem-plan-guard` refuses edits outside the workspace folder (`WORKITEM_WORKSPACE`), so code stays read-only and items and plans can be written. When the human asks, the session may also edit the workspace's board files and skills (`boards/<board>.json`, `skills/`, `boards/<board>/skills/`); the prompt says so, and also that existing workitems are not edited (their stage changes only through `workitem-move`). Its prompt lists the boards with their repos; asked for workitems, it runs `workitem-create` once per board and records each with `workitem-plan-note --workitem <dir>`, which appends to the record's `workitems` list.
50. **No current-directory lookup** (skills, `workitem-move`). Nothing finds items through `git rev-parse` any more. Skills get `WORKITEM_FILE` from the launcher, or an explicit path or `--workspace`/`--board`. `workitem-move` takes a path only (`--list` and bare dir names are gone). `/workitem-run` and `/workitem-watch` are deleted: the dispatcher and `watch/pr-review` replaced them (9, 40).
51. **UI** (frontend). The header has a workspace picker instead of the project filter, and exactly one workspace is in view; there is no "all workspaces". Board tabs show the workspace's boards with their repo's folder name, always (one board is still a tab). The URL is `#<workspace>/<dir>[/<tab>]?board=<name>` for an item, `#?workspace=<name>&board=<name>` without one, and `?plan=<workspace>/<id>` for a plan; `workspace=` is left out when the item or plan names it. Search stays global and switches workspace to open a hit. *Add board* sits next to the tabs. The API is `/api/workspaces/{workspace}/...` and `/api/workitems/{workspace}/{dir}/...`, and items carry `workspace` instead of `project`.
52. **Agent per workspace** (39; kinds and a default in 56). `agent` lives in `workspace.toml` and is set from the header as before (`PUT /api/workspaces/{name}`).
53. **Migration** (`bin/workitem-migrate`). `workitem-migrate --to-workspace <name> --board <board> <repo>` moves `<repo>/.workitems` (or `.claude/workitems`) into `~/.workitems-pipeline/workspaces/<name>/`; run it once per repo to put several repos in one workspace. The repo's default board (`boards/default.json`, `pipeline.json`, or the bundled file when it has none) becomes `boards/<board>.json` with `repo` set, and its other boards become `<board>-<name>`; their folders (`boards/<name>/`) move along. Items get `board:` rewritten to the new names. The repo-level `skills/` and `watch/` are copied into the folder of every new board (a board's own files win), and `learnings.md` goes to the default board's folder; the repo's project `agent` in the old config becomes the workspace's when it has none. Plans move to `plans/`. It refuses before touching anything when a target file exists (two repos with the same item dir), when a `wi-*` session of that repo is running, or when the workspace already has a board of that name, and leaves files it does not know where they are, listing them. Paused columns and watcher times are not carried over.
54. **A board without a repo** (45, `pipeline.rs`, `launch.rs`, `watch.rs`, `workitem-move`). `"repo"` may be left out, for a board whose items change no code (an intake board that turns a Product Discovery idea into delivery tickets). Such a board has no worktrees and no PRs, so a PR stage or `pr_status` on it makes the file invalid, and the fixer, merge, rebase and PR tab actions answer 409. Its item sessions start in the item folder (`<workspace>/<dir>`) without `WORKITEM_REPO`, with `--add-dir` for the workspace and every other board's repo and the repos' `CLAUDE.md` read (like plan sessions, 49), so the agent can read the code it plans for. Its watchers run in the workspace folder, also without `WORKITEM_REPO`. `repos()` skips it, the board list in create and plan prompts says "no repo", and the tab shows no repo name. *Add board* still asks for a repo, because the bundled template has a PR stage.

55. **Workspace watchers** (38, 40, 44; `config.rs`, `watch.rs`). `workspace.toml` can carry `[[watch]]` tables (`every`, `command`, optional `args`, the shape of a board watcher). Each runs once per workspace, however many boards it has: stdin holds every item of the workspace, the script runs in the workspace folder, `WORKITEM_BOARD` and `WORKITEM_STAGE` are empty and there is no `WORKITEM_REPO`. Scripts resolve from the workspace's `watch/`, then the bundled folder. The last start is kept in `watch.json` as `workspace/@workspace/<i>` (`@` is never in a board name). `pr-status` and `issue-status` read every item in one batched call whatever its board or repo (GraphQL grouped by the repo in each PR URL; one Jira search per 100 keys), so running them per board or, worse, per stage only multiplied the calls: a board file that names either is invalid and says to move it to `workspace.toml`. A workspace with a board that needs its PRs read (40) and no `pr-status` of its own gets an implicit one every 1m, since `pr-review` waits for its readings; `issue-status` is never implicit, a workspace lists it. An invalid `workspace.toml` keeps its last valid version (like a board, so a typo neither stops the PR reader nor drops the agent) and its error shows in the header; *Agent* refuses to save over an invalid file and otherwise changes only `agent` in it (comments are lost). The *Watchers* link in the header lists them read-only (implicit ones marked); there is no pause, since neither script starts anything and the PR stage's own pause still holds back `pr-review`.
56. **Agent kinds and a default agent** (39, 52; `config.rs`, `launch.rs`, `plans.rs`, `skills/workitem-pipeline/agents/`). Sessions can run Claude Code, opencode, pi or omp, every session including planning ones. The agent is `agent = { kind = "...", command = "..." }`, with `kind` one of `claude`, `opencode`, `pi`, `omp` and `command` defaulting to the kind's name (for Claude, to `WORKITEM_UI_CLAUDE`); a wrapper like `yolo` still works. It is set in `config.toml` as the default of all workspaces (`GET/PUT /api/agent`) and in `workspace.toml` as an override (`PUT /api/workspaces/{name}` with `{"agent": {...}}`, `null` clears it); without either, Claude runs. An old `agent = "yolo"` string reads as `kind = "claude"`, and a save writes the table form. The save checks that the executable resolves. `GET /api/agent` also lists the kinds with `installed` (their own CLI found on `PATH`), and the workspace settings dialog (71) marks the others "not found on PATH" but keeps them selectable, since a command can name another executable; a link there opens the default's dialog. Rust maps each kind's arguments (`launch::agent_args`) from the folders a session adds (46, 49, 54), the stage's model (60) and the item's MCP server (61): Claude `--add-dir` plus `--settings`; omp `--add-dir=<dir>` per folder plus `-e <glue>`; pi `-e <glue>` (it has no permission prompts, so it reaches every folder); opencode `OPENCODE_CONFIG_CONTENT`, which opencode merges over the user's config (providers and MCP servers stay), with the glue as a `file://` plugin and `permission.external_directory` allow rules for exactly those folders and the pipeline's skill folder (both its path and its real path, since `install.sh` symlinks it); everything else keeps the user's setting, so a prompt there shows as blocked. The model is passed through unchanged: Claude and pi `--model <model>`, omp `--model=<model>` (a fuzzy match, so Claude's `opus` works), opencode `-m <model>` only for a `provider/model`; it refuses a Claude alias like `opus`, so it gets no flag then and uses its own default. The MCP server: Claude `--mcp-config <file>`; opencode a `remote` entry in `OPENCODE_CONFIG_CONTENT` whose `Authorization` header is `Bearer {file:<path>}`, since the env reaches tmux in argv and the token must stay in a 0600 file like the config (61); pi has no MCP client and omp reads MCP servers only from files in the repo or the user's home, so for both the launcher sets `WORKITEM_MCP` to Claude's config file and their glue (`agents/mcp.ts`) registers the server's tools (`tools/list`) as its own, proxying each call (`tools/call`) to the server; the tools stay the server's, and a refusal is the tool's error. The prompt comes last; opencode takes it as `--prompt <prompt>`, which submits it. The glue is code in each CLI's plugin format, `agents/<kind>/workitem-notify.ts` sharing `agents/notify.ts`, and does nothing without `WORKITEM`, `WORKITEM_PLAN` or `WORKITEM_CREATE` in the env. It runs `bin/workitem-notify` with Claude's `notification_type` on stdin, so the blocked and waiting rules stay in that script: opencode reports `permission.asked` and `question.asked` as needing a human and `session.idle` of a session without a parent (not a subagent's) as idle; pi reports `agent_end`; omp `tool_approval_requested`, `plan_review_requested` and its `ask` tool as needing a human and `agent_end` as idle. pi and omp report idle only after the agent stayed stopped for a second (a following `agent_start` cancels it). In a create session (75) the same reports set the toast's waiting, and the agent going on (opencode: `session.status` busy and `permission.replied`; pi and omp: `agent_start`; omp also `tool_result`) runs `workitem-notify --resume`, as Claude's `UserPromptSubmit` and `PostToolUse` hooks do. In a planning session the glue does what Claude's planning hooks do: it refuses edits outside the workspace folder through `bin/workitem-plan-guard` (opencode: `tool.execute.before` throws; pi and omp: `tool_call` returns `block`; only tools named like edit, write or patch, so reading stays free), and marks the record `working` when the agent starts or goes on (opencode: `session.status` busy; pi and omp: `agent_start`; omp also `tool_result`). The guard does not see shell commands, so they ask the human first, as Claude's planning settings do, except a plain call of `workitem-plan-note`: opencode gets `permission.bash` `ask` with an `allow` rule for the helper in the planning session's `OPENCODE_CONFIG_CONTENT`; pi, which has no permission prompts, asks in its `tool_call` with `ctx.ui.confirm` and reports it as a permission prompt; omp asks for tool approval already. The plan record keeps `agent: <kind>` and `agent_session: <id>`, and Resume runs that kind (the workspace's agent when it is that kind, else the kind's own CLI). Claude and pi take the id from the launcher (`--session-id`); opencode and omp pick their own, and their glue records it with `workitem-plan-note --agent-session` (opencode: the first session without a parent; omp: its session file). Resume: Claude `--resume <id>`, opencode `--session <id>`, pi `--session-id <id>`, omp `--resume=<file>`. Older records hold a Claude conversation as `claude_session`, which Resume still reads. The skills reach the issue tracker only through `bin/workitem-issue` (66), so they need no tool of the agent's, and the plan prompt points at `workitem-create/SKILL.md` instead of naming a Claude skill. `workitem-start` Step 4b (a background `Agent`) stays Claude-only; the UI never uses it. Tests: a Rust test runs a recording stub per kind for item sessions (model, MCP), create sessions, plans and Resume; `agents/glue.test.mjs` (`node --test`, part of `npm test`) feeds each glue fake events and checks what the real scripts write, and that pi's and omp's MCP tools reach a fake server; `WORKITEM_LIVE_AGENTS=opencode,pi,omp cargo test --test pipeline live_agents` runs the real CLIs and checks that a stopped agent blocks its item and that a plan records its session and turns waiting.
60. **Model per stage** (`pipeline.rs`, `launch.rs`). A stage can name a `model`; every item session started while the item is in that stage (handler, fixer, Start session, Discuss brief) gets `--model <model>`, so the same skill can run on different models on different boards, and inline-prompt stages are covered too. A skill's frontmatter `model:` is ignored, because the launcher strips the frontmatter. Without `model` no flag is passed and the agent's own default applies (settings, `ANTHROPIC_MODEL`, the workspace `agent`); Create and Plan sessions have no stage and always use it. The value must be letters, digits and `. _ : - / [ ]` (`/` for opencode's `provider/model`, 56), not starting with `-` (a typo, not a security check: it is one argv element); anything else makes the board invalid. There is no list of known models, so aliases, full IDs and names only a custom agent knows all work. The Settings tab of the stage dialog (decision 76) shows and edits it, empty meaning the agent default; the cards do not.
61. **Questions to the parent over MCP** (`questions.rs`, `launch.rs`). An item asks its parent item (`parent:`) through an MCP server the backend serves per item at `/api/mcp/<workspace>/<dir>` (Streamable HTTP, JSON responses only, Bearer token like `/run`), not through the terminal, so any agent with an MCP client can take part and nothing reads or types into a pane. Tools: `ask_parent` (records the question in the item's `questions.json`, sets `blocked: asking parent: <question>` and waits up to `ask_wait`, 240s, for the answer), `wait_for_answer`, `list_child_questions` and `answer_child` (only the parent may answer, and only a parent with `answers_children: true` is asked: something must answer, and otherwise the child asks in its terminal as before; once nothing is open the block lifts to `working` while the asker's session waits, else `ok`, so its handler runs again and finds the answer in the file). The backend decides nothing beyond that: who answers, and when the human is asked, is the parent's board's business (on the features board its `children` watcher starts a resolver on the parent). Every item session gets `--mcp-config` with a file in `<root>/mcp/` (mode 0600, because argv is public), `hooks.json` allows `mcp__workitem`, and the session protocol tells an item with a `parent:` to ask with `ask_parent`. Registering the server is the agent-specific part; decision 56 maps it for each agent kind (opencode through its config, pi and omp through their glue), and a `claude` kind's command must accept `--mcp-config` like the other Claude flags. Permission prompts stay in the terminal. Rejected: Claude Code's `SendMessage` between named sessions (Claude-only, and messages live only while both sessions run) and a shell helper polling a file (depends on the agent calling it again).

### Issue trackers and GitHub accounts (built)

Decisions 62 to 72 let a workspace use GitHub Issues instead of Jira and its own GitHub account. The code host stays GitHub; PRs get no provider seam until a second host exists (`pr-status` writing facts that `pr-review` reads is already where one would go). Bitbucket and GitLab are not built.

62. **Issue tracker per workspace** (`config.rs`). `workspace.toml` carries `issue_tracker = "jira" | "github"`; missing means `jira`, so existing workspaces do not change. It is the authority: every tracker operation dispatches on it, and a ref of the other tracker's shape is refused with a message. New trackers (GitLab) are new values.
63. **GitHub issue refs** (`workitem-issue`). `issue:` holds the full `owner/repo#123`, unique across boards and repos and unchanged when an item moves board. The frontmatter keeps the existing `<ref> (<url>)` shape (`issue: acme/web#123 (https://github.com/acme/web/issues/123)`), which `ticket()` in the frontend already renders, so the card badge needs no change. Input may be `#123`, `owner/repo#123` or an issue URL; a bare `#123` is expanded with the board's `issue_project` (64). Folder and branch prefix is `<repo>-<n>-<slug>` (`web-123-dark-mode`), with every character of the repo name other than letters, digits and `-` turned into `-` (`next.js` gives `next-js-42`), because tmux changes `.` in session names and `wi-<dir>` would no longer be found. `read`, `set-state` and `pr-line` refuse an `issue:` of the other tracker.
64. **`issue_project` on a board** (`pipeline.rs`). Where a new issue is filed and what a bare `#123` means: `owner/repo` for GitHub (default: the board repo's GitHub remote, `gh repo view --json nameWithOwner` in its `repo`), a project key for Jira (no default: creating refuses with "set `issue_project` on board X"). A board without a repo in a GitHub workspace must set it. Validated with the board file: `owner/repo` shape for GitHub, `[A-Z][A-Z0-9]+` for Jira.
65. **GitHub issue states** (`workitem-issue`, `watch/issue-status`). No transitions and no labels or Projects. The only states a stage can set (72) are `assigned` (to `@me`) and `closed`; the bundled defaults assign on development and set nothing on review. The PR body carries `Closes owner/repo#123`, so the merge closes it (only for a PR into the default branch). `issue-status` maps open and unassigned to `Open`/`new`, open and assigned to `In progress`/`indeterminate`, closed to `Closed`/`done`, the categories the board already sorts and colours by.
66. **`bin/workitem-issue` owns every tracker operation** (skills stay tracker-neutral). Commands, each taking the item file so the script finds the workspace (`issue_tracker`, `github_account`) and the board (`issue_project`, `repo`) itself: `parse <item> <input>` prints `<ref> (<url>)` and the folder prefix (also with `--workspace --board` for `workitem-create`, before the file exists); `link <item> <input>` writes that `issue:` into an item that has none, so no agent types it by hand (an agent once dropped the URL, leaving a badge without a link); `read <item>` prints title, status, body and comments as markdown (each comment under `## Comment by <author>`, then a `Posted <time> · id <id>` line, so a watcher can tell new comments apart); `search <item> <words>...` (also with `--workspace --board`) prints the open issues of `issue_project` matching the words, one `ref<TAB>status<TAB>labels<TAB>summary` line each, in the tracker's order (the caller ranks by label if it needs to; Jira: JQL `text ~` with Lucene syntax characters dropped and the words lower case, so any words make a valid query; GitHub: `gh issue list --search`); `create <item> --title T --body-file F` files the issue in `issue_project` and sets `issue:`; the `issue-status` watcher also adds the URL to an `issue:` that holds only a key the tracker found; `comment <item> --body-file F` posts a comment on the item's issue (Jira: ADF paragraphs on blank lines, hard breaks on single newlines); `set-state <item> <state>...` moves the issue to the first of the states that exists (called by `workitem-move`, 72); `pr-line <item>` prints the PR body line (`Closes owner/repo#123`, the Jira key, or nothing). It skips on `issue: none`, when another item `depends_on` this one (only the last of a chain moves the shared issue, 48), and when the issue is already in the target state. In `set-state` a missing transition or an API error exits 0 with a warning (the handler notes it and goes on); in the other commands an API error exits 1, so a failed `comment` stops its caller. A bad ref, missing config, an unreadable or empty `--body-file` or (for `comment`) no linked issue exits 2. Jira moves from the Rovo MCP tools to REST with jira-cli's credentials, in a module shared with `issue-status`; the skills lose their Atlassian `allowed-tools`.
67. **GitHub account per workspace** (`config.rs`, `launch.rs`, `watch.rs`, `review.rs`, `actions.rs`). `workspace.toml` carries `github_account = "<login>"`. On every start (item session, watcher run, the backend's own `gh` calls) the backend runs `gh auth token --user <login>` and sets `GH_TOKEN` on the process, so workspaces never share gh's global active account. A token gh gave is kept in memory for a minute, so the dispatcher (which holds `busy`) does not start a `gh` per workspace on every 5s pass; a failure is never kept, so a fresh `gh auth login` applies on the next tick. Missing means gh's active account. `git push` follows the repo's remote: HTTPS with gh's credential helper picks up `GH_TOKEN`, SSH uses whatever key `~/.ssh/config` picks (an SSH host alias per account); the pipeline does not manage keys.
68. **Fail closed on a missing account** (67). When the token cannot be resolved, that workspace starts no sessions and no watchers and shows a workspace alert (`GitHub account <login> is not logged in: run gh auth login`); other workspaces keep running and it retries every tick. Falling back to the active account was rejected: an agent would push, comment or merge as the wrong identity.
69. **Jira credentials stay global** (66). jira-cli's config and token, as `issue-status` reads them today. A per-workspace `jira_config` waits for a second Jira site.
70. **`reviewers` on a board** (`workitem-start`). `"reviewers": "org/team"` is the team *Mark ready for review* adds; missing means none is added. Replaces the hardcoded `<owner>/backend`.
71. **Where the keys are set** (`Workspaces.tsx`, `api.rs`). The workspace dialog gets an `issue_tracker` select and a `github_account` input next to `agent`, written like `agent` (only that key changes). Saving checks every key before writing any: a changed `github_account` must give a token (`gh auth token --user`; an unchanged one is not checked, so a broken saved account does not block the other settings), and a changed `issue_tracker` is refused while a board's `issue_project` or `issue_state` would not suit it, naming those boards. *Add board* gets optional `issue_project` (the derived `owner/repo` as placeholder) and `reviewers`; later changes are file edits, like `repo`. UI text that says "Jira" says "issue".
72. **Issue state per stage** (`pipeline.rs`, `workitem-move`). A stage can carry `"issue_state": ["In development", "In Progress"]`; after a successful move into it, `workitem-move` runs `workitem-issue set-state <item> <states>`, which picks the first state the issue can move to. Best effort like the rest of 66: a missing transition or an API error warns and the move stands (the backend runs `workitem-move` without blocking a worker thread, since it may wait on the tracker), and the skip rules (no issue, a `depends_on` chain, already there) live in `workitem-issue`. Because it hangs on the move, manual moves from the UI update the issue too, and `workitem-start` has no tracker steps left. Per board, since Jira projects differ in workflow; a GitHub board may only name `assigned` and `closed`, checked with the board file. On a Jira board `assigned` is not a status: it also assigns the issue to the API user, replacing another assignee (a Jira issue has one), before the transition, so a missing transition does not skip it. The bundled `pipeline.json` carries none; *Add board* fills in the defaults for the workspace's tracker (Jira: `In development`/`In Progress`/`assigned` on development, `In Review` on the PR stage; GitHub: `assigned` on development). A per-workspace table was rejected: it ties states to skill steps rather than columns and cannot differ between two boards.
73. **Board settings in a dialog** (`BoardSettings.tsx`, `pipeline.rs`). A gear button at the right end of the top bar, after *New workitem*, opens a form for a board's top-level `label`, `entry`, `order`, `issue_project` and `reviewers`; `PUT /api/workspaces/<ws>/boards/<board>` writes them. `repo` is shown read-only and the route refuses it, since items, worktrees and branches hang on it; renaming a board is left out for the same reason; deleting one takes its items with it (decision 77). Stages, watchers and `brief_sections` stay file-only: they are nested and a form for them is a large build. The file is read as JSON, only those keys are set (an empty optional one is removed), every other key keeps its place, and the result must pass `Pipeline::parse` and the tracker check before it replaces the file, so a save never makes a board invalid. The file is rewritten pretty-printed. Last write wins for those keys; a hand edit of the stages made meanwhile is kept, as the file is read at save time.
74. **Triage folded into analyze** (`workitem-analyze`, `pipeline.json`). A Claude session that only set `analyze_mode` cost a full start per item, so `workitem-analyze` now picks the mode itself when `analyze_mode` is missing (same rules: validate, root_cause, clarify; too vague → `agent_status: blocked: <what is missing>`). The bundled board has no `backlog` stage: `entry` is `analyze`, and analyze's `next` is only `ready_for_development`, so an item that is not actionable stays in `analyze` with `agent_status: blocked: <reason>` instead of moving back. The `workitem-triage` skill is gone; a board file copied from the older template still names it and must drop its `backlog` stage. The `review` board keeps its `backlog`, a real queue filled by `pr-review-intake`. Create sessions (`wi-new-*`) are toasts (decision 75); there is no column for them.
75. **Create sessions as toasts** (`ActivityToasts.tsx`, `createToasts.ts`, `launch.rs`, `workitem-notify`). A link at the end of the Plans section was easy to miss and could not say when the agent waited for an answer. Each `wi-new-*` session is now a toast above the activity toasts, outside their "+N more" count, derived from the `/api/sessions` poll so it survives a reload. *Running*: a spinner, the workspace and **Open terminal ↗**, no close button, since the toast is the only way to the session. *Needs your answer*: amber, the same link, and the blocked beep. *Created*: the session is gone and items name it in `created_by:`, one row per item (a split), each opening it; it counts down like the others. *Ended without a workitem*: the session died (`remain-on-exit` keeps its pane, so the toast keeps the terminal link) or went away with no item after two item polls; it counts down too. Create sessions get inline `--settings` instead of the shared `hooks.json`: `Notification` runs `workitem-notify`, which sets the session option `@workitem_waiting` (found through `WORKITEM_CREATE` and the inherited `$TMUX`), and `UserPromptSubmit` and `PostToolUse` run it with `--resume`, which unsets it; `/api/sessions` returns `waiting` and `dead`. The create prompt (not the generic `workitem-create` skill) tells the agent to write `created_by: <session>` into every item it writes; `Item.created_by` is empty without it. Dead create sessions are not reaped, because that would lose the terminal link to the crash output; × on the *Ended* toast of a dead one kills it with `DELETE /api/sessions/<workspace>/<name>`, which refuses names that are not `wi-new-*` (400), sessions of other workspaces (404) and live ones (409). The countdown does not kill, so a toast that only timed out comes back after a reload.
76. **Stage settings in the stage dialog** (`StageSource.tsx`, `pipeline.rs`). The gear button in a column header opens the stage dialog with two tabs: *Settings* (default) and *What runs* (the read-only skill or prompt and scripts). Settings edits only the stage's `model` (decision 60) and whether entering it needs a linked issue (`require: {"issue": "linked"}`, which `workitem-move` enforces); `PUT /api/workspaces/<ws>/boards/<board>/stages/<stage>` writes them to the workspace picked in the dialog. An empty model removes the key; turning the issue off removes `require.issue` and a `require` left empty. Other `require` keys (`approved`, `brief`, `depends_on`, `children`), the order of the stages, handlers and watchers stay file-only. Same save rules as decision 73: the file is read at save time, only those keys change, the result must pass `Pipeline::parse` and the tracker check before it replaces the file, and last write wins.
77. **Delete a board with its items** (`BoardSettings.tsx`, `actions.rs`). *Delete board* in the board settings dialog asks for confirmation, naming how many workitems go with it and that branches and PRs stay, then `DELETE /api/workspaces/<ws>/boards/<board>` removes every item of the board the way *Remove* does (session stopped, worktree removed without `--force`, folder deleted), then `boards/<board>.json`, `boards/<board>/`, the board's last valid file, its paused stages and its watchers' start times. It holds `busy` throughout, so the dispatcher never starts a handler on an item mid-delete. Items go first: an item folder that cannot be deleted stops it with the board intact, so no item is left on a missing board; a worktree git refuses is reported and does not stop it. `parent:` and `depends_on:` on other boards that name a deleted item are left as they are, as with *Remove*.
78. **One snapshot per poll** (`api.rs`, `pipeline.rs`, `App.tsx`). The board polls `GET /api/state`, which returns `workspaces`, `pipelines`, `items`, `sessions` and `plans` in the shapes of their own endpoints, read from one list of workspaces and one `tmux list-sessions` (plus one look for dead panes), so the parts agree and a tick costs two tmux calls instead of five. An action reloads the whole snapshot. The five old endpoints stay until nothing uses them; the detail and plan panels keep their own polls. `AppState::pipeline` reads a board file again only when its modification time or length, or the workspace's `issue_tracker`, changed; the cache entry is the last valid board of decision 20 plus the last error, so an invalid file is logged once per change, not once per call. A file that cannot be looked at is read on every call, as before.
79. **Opt-in remote access** (`main.rs`, `auth.rs`). To reach a running server from another machine, `WORKITEM_UI_HOST` sets the bind address (default `127.0.0.1`, so decision 1 holds unless it is set) and `WORKITEM_UI_ALLOWED_HOSTS` (comma list of host names or IPs, no port) adds names the Host check accepts with the server's own port, next to `127.0.0.1` and `localhost`. The Host check stays the DNS-rebinding guard: a name not listed gets 403 even when the bind is open. The startup line prints one `#token=` URL per accepted name (`127.0.0.1` for an unspecified bind like `0.0.0.0`). Internal callers (MCP URL, `workitem_api.py`) keep using `127.0.0.1`, so the remote setup binds `0.0.0.0` (or `::`), not one LAN address. No TLS: the token and terminals travel in clear text, so this is for a trusted network.
80. **Worktrees in the workspace folder** (`git.rs`, `launch.rs`, `workitem-start`, `workitem-remove`). An item's worktree goes to `<workspace>/.worktrees/<repo-name>-<dir>` instead of next to the repo, so a workspace keeps all its state in one folder and the repo's parent folder does not fill up with checkouts. Not in the item folder: removing an item (and *Delete board*, 77) deletes that folder even when git refused `git worktree remove` for local changes, which would lose them, and the file browser walks the item folder with a 1000-entry cap that a checkout fills. `.worktrees` starts with a dot, so it is never an item (item dirs are slugs, and the item list keeps only folders with a `workitem.md`). `workitem-plan-guard` refuses edits under `.worktrees/`, so planning sessions still change no code (49). Item sessions get the path in `WORKITEM_WORKTREE`, so `workitem-start` never computes it; the fixer and manual-session prompts name it too. Worktrees are found by folder name (`git::worktree_for`), so ones made next to the repo before this keep working, and `worktree_path` names that old place while it exists; nothing is moved.
81. **Allowed hosts behind a reverse proxy** (`auth.rs`, `main.rs`; amends 79). A proxy with its default config (e.g. Nginx `proxy_set_header Host $host`) sends `Host: foo.bar.com` without the server's port and passes the browser's `Origin: https://foo.bar.com`, so 79's checks refused both. Now a `WORKITEM_UI_ALLOWED_HOSTS` entry may be a name, an IP or a URL (`https://foo.bar.com/`), and only its name counts: scheme, port and a trailing `/` are dropped, and names compare case-insensitively. A listed name passes with any port or none; `127.0.0.1` and `localhost` still need the server's own port. The DNS-rebinding guard rests on the name, which a page on another site cannot make the browser send, so the port adds nothing for a listed name. `/ws` accepts `Origin` `http://<Host>` or `https://<Host>`: still same-origin on the name, only the scheme is free. The startup line prints a URL entry as given (`https://foo.bar.com/#token=...`). With TLS at the proxy, 79's clear-text caveat does not hold for that route. Not covered: a proxy on a non-default public port (`https://foo.bar.com:8443`), whose `Host` loses the port while `Origin` keeps it, so `/ws` gets 403.
82. **Remove forces the worktree** (`actions.rs`; supersedes the "never `--force`" of 9 and 77). A worktree with modified or untracked files made `git worktree remove` fail, so *Clear* on the final column left such worktrees behind. *Remove*, *Clear* and *Delete board* now run `git worktree remove --force`: the dialogs already say the worktree is deleted. Uncommitted and untracked files are lost on purpose; the branch (committed work) and the PR stay. What a single `--force` does not cover (a locked worktree) is still reported as the worktree left behind. The `workitem-remove` skill keeps refusing a dirty worktree, since it asks the user first.
83. **Sessions and watchers do not inherit the outer item's vars** (`launch.rs`, `watch.rs`). A tmux session gets the tmux server's global env besides its `-e` values, and the server copies that from the process that started it: when that is a test run or a backend started from an item session (`wi-<dir>`), it holds that item's `WORKITEM_*`, so a session on a board without a repo got the outer `WORKITEM_REPO` and `WORKITEM_WORKTREE`. `launch::start` now runs the command under `/usr/bin/env -u <var>` for each var the launcher sets on some session (`WORKITEM`, `WORKITEM_FILE`, `WORKITEM_REPO`, `WORKITEM_WORKTREE`, `WORKITEM_CREATE`, `WORKITEM_PLAN`, `WORKITEM_MCP`, `OPENCODE_CONFIG_CONTENT`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`) but not on this one. Unset, not `-e VAR=`: `workitem-start` tests whether `WORKITEM_WORKTREE` is set. `GH_TOKEN` stays inherited: a workspace without `github_account` relies on it (67). A watcher without a repo drops the backend's own `WORKITEM_REPO` the same way. The tests' `remove_var` workaround is gone.
84. **Unresolved stage files on the board** (`api.rs`, `Board.tsx`). A valid board whose stage names a handler skill, fixer skill or watch script that does not resolve looked fine; the error only showed in the stage dialog or when a launch failed (the `workitem-fix-*` skills before `install.sh` was re-run). `BoardInfo` gets `problems` (stage name to messages, only stages with any), computed from the board in use (also when the file on disk is invalid, 20) by `StageFiles`, the same resolution `.../source` uses, so the board and the dialog cannot disagree. Only file lookups, no reads, since it runs on every snapshot poll (78). The column header shows a warning icon with the messages as tooltip, and the board banner gets one line per problem. Workspace watchers are not per stage and are not covered.
85. **Board problems panel and fix agent** (`BoardProblems.tsx`, `actions.rs`, `launch.rs`; amends 84). One red line per problem was hard to read: messages carry long search paths. The banner is now one panel per workspace: a header with the count and a *Fix with agent* button, then one row per problem (the board file first, then stages in column order), the gist in bold and the folders a resolver looked in behind a collapsed *Looked in N places* (`splitProblem`). The button calls `POST /api/workspaces/{workspace}/boards/{board}/fix`, which recomputes the problems itself (never trusts the page) and refuses a board without any (409); it starts a `wi-new-fix-<id>` session like a create session (workspace folder, every board's repo added, create settings, so it shows as a toast and reports when it waits). Its prompt lists the problems, the board file, the resolution order and the `install.sh` hint, says not to touch workitems, to ask when the fix is unclear, and to kill its session when done. `AgentSession.purpose` (`create` or `fix`, from the name) lets the toast say *Fixing board…*, and while a live fix session of the workspace exists the panel shows it with a terminal link instead of the button, so one click does not start two. The column marker stays.
86. **Old polling endpoints removed** (`lib.rs`, `api.rs`, `plans.rs`, `api.ts`; closes the "five old endpoints stay" sentence of 78). Nothing polled `GET /api/workspaces`, `/api/pipelines`, `/api/workitems`, `/api/sessions` or `/api/plans` any more: the board reads `/api/state`, scripts and the MCP glue only use `/api/workitems/{workspace}/...` and `/api/mcp/...`. The five GETs and their handlers are gone (an `/api/...` path without a route is 404; `/api/workspaces` keeps `POST`), as are the unused client functions; the tests read the same parts from `/api/state`. One list read means one place that decides what the board sees.

82. **Bitbucket Cloud PRs via bkt** (`watch/pr-status`, `watch/pr-remind`, `review.rs`, `actions.rs`, `bkt.rs`, `api.rs`, `config.rs`, the start and fix skills; lifts the "only GitHub" non-goal). A second code host for the PR stage. The provider comes from the `pr:` URL host — `bitbucket.org/<workspace>/<slug>/pull-requests/<id>` — so no provider key exists anywhere: `pr-review`, the frontend and the `pr_*` facts mean the same on both hosts. The Bitbucket reader is the `bkt` CLI (github.com/avivsinai/bitbucket-cli): watchers take `WORKITEM_BKT` and `WORKITEM_BKT_CONTEXT`, the backend `WORKITEM_UI_BKT`, and `bkt_context = "<name>"` in `workspace.toml` picks the credentials (decision 68's fail-closed rule): saving a changed context probes `bkt context list --context <name>` (`bkt.rs::context_for`), which also fails when the context has no token. `pr-status` batches differently than gh GraphQL: one `bkt api` list call per repo for the open PRs, one per head commit for its date, one per PR for its build statuses, comments only for moved PRs. Cloud has no changes-requested verdict, so `pr_approval` is only approved | none, and every build status counts as required (`pr_ci_required` == `pr_ci`); an unknown answer fails closed to pending, never passing. Two Cloud quirks the readers encode: `bkt pr view --json` returns the PR nested under `pull_request` (every reader and stub must use that one shape), and a comment mention through the API needs the account id (`@{<account_id>}`, the uuid without its braces as fallback — a plain `@nickname` notifies nobody). Merge is `bkt pr merge <id> --strategy squash`; rebase has no server-side call, so it fetches base and branch in the board repo, rebases in a temporary detached worktree — never the board repo's own checkout, which a rebase would detach and refuse on uncommitted changes — and pushes with `--force-with-lease`, aborting the rebase and removing the worktree on failure. Bitbucket Issues are out of scope: `issue_tracker` stays `jira | github`.

83. **The PR host behind one interface** (`bin/workitem_pr.py`, `bin/workitem-pr`, `watch/pr-status`, `watch/pr-remind`, `review.rs`, `actions.rs`, the start, remove and fix skills; mirrors 62 to 72 for PRs). 82 chose between GitHub and Bitbucket in three runtimes (the backend, the watchers, the skills' prose) with three copies of the link parser, and most of its review findings were those copies disagreeing (`#fragment`, host case and port, two shapes expected from `bkt pr view`). Now `workitem_pr.py` holds the one parser (`parse`: host lower-cased, port, user info, query, fragment and any suffix after the number ignored; `bitbucket.org/<ws>/<slug>/pull-requests/<n>` is Bitbucket, `<host>/<owner>/<repo>/pull/<n>` on any other host GitHub) and a `GitHub` and a `Bitbucket` provider with the same methods: the batched reads `pr-status` needs (GitHub stays one GraphQL query per repo and 25 PRs), threads, conversation, mentions, comment, reply, checks, failed log, base, state, ready, add reviewers, merge and rebase. Bitbucket maps its states, build statuses, approvals and comments onto the GitHub vocabulary inside its class, and reads every PR through the Cloud REST pull request (`bkt api`), so there is one shape. `bin/workitem-pr <verb> <workitem>` is the CLI over it, taking the item file like `workitem-issue` so it finds the PR, the workspace (`github_account`, `bkt_context`) and the board's repo itself; errors exit 2 (setup, input) or 1 (host) and always carry a message. The watchers import the module; the backend runs `workitem-pr merge|rebase <item>` and `workitem-pr conversation <item> --json`, with `GH_TOKEN`, `WORKITEM_GH`, `WORKITEM_BKT` and `WORKITEM_BKT_CONTEXT` set (`review.rs::workitem_pr`), and keeps only the PR stage check and the settings probes (`github.rs`, `bkt.rs`). The skills call `workitem-pr` and never `gh` or `bkt` for a PR. `gh` and `bkt` run with stdin closed, so a prompting CLI fails instead of hanging a watcher. The Bitbucket rebase moves to Python unchanged (temporary detached worktree, `--force-with-lease`, abort and cleanup on failure). The `bkt_context` probe of 82 is two calls: `bkt context list` must name the context, then `bkt api /user` must succeed (an empty error falls back to the exit status). PR creation (`/create-pr`) and the global skills outside this repo keep using `gh`.

86. **Waiting on CI is the spinning CI icon** (`boardState.ts::agentLine`, `AgentStatus.tsx`, `DetailPanel.tsx`). Card and detail panel header alike. Other waiting reasons keep the text.

87. **Stage actions** (`pipeline.rs`, `api.rs`, `actions.rs`, `watch.rs`, `actions/pr`, `StageActions.tsx`; replaces the hard-coded *Merge PR* and *Rebase onto base* buttons and the `merge` and `rebase` routes). A stage can list `actions: [{label, skill | script, when, confirm, args}]`: buttons in the detail panel's header, under the gate bar, for the items in that stage whose frontmatter has every `when` value (raw values, the rule `run-items` applies to the stage `when`). The label is the action's id, unique within the stage, so a board edit between render and click cannot run another action under the old confirm text. The API puts `actions: [{id, label, confirm, starts_session}]` on each item, already filtered, so the frontend knows no conditions (16); `Workitem` keeps the whole frontmatter (not serialised) for this. `POST .../action/{id}` checks stage and `when` again (409 when the item no longer matches). A `skill` starts as the item's `wi-<dir>` session through `dispatch::run_handler` with that handler, like `/run` (the session is the lock); `starts_session` marks it; the panel disables it while the item has a session or its `agent_status` is not `ok` (`run_handler` refuses both), and switches to the *Terminal* tab when it starts one. The bar keeps the last outcome while no action matches any more, so a failed merge whose re-read hides every action still says why. A `script` comes from `actions/` folders resolved like watch scripts (board, workspace, bundled), runs once like a watcher of the stage (no shell, its env vars, `GH_TOKEN`, `args`, in the board's repo or the workspace folder) with the one item as a JSON object on stdin, and is killed after 20 min, above a Bitbucket rebase's own limits (83; `actions/pr` execs `workitem-pr` rather than running it as a child, so the kill reaches it); a non-zero exit is a 409 whose message is its stderr. After a script the workspace's `pr-status` and the stage's watchers are made due and the dispatcher woken, as the old merge route did. Every key is checked when the board is read, and a bad action (no label, both or neither of `skill` and `script`, a `script` that is not a plain name, `args` with a `skill`, a duplicate label, an unknown key) rejects the file whole (20). An action skill or script that does not resolve is a problem of its stage on the board (84), like a missing handler. Merge and rebase are one bundled script, `actions/pr merge|rebase`, which runs `workitem-pr` (83) on the item; the bundled board's PR stage lists *Rebase onto base* (`when: {pr_state: open}`) and *Merge PR* (`when: {pr_state: open, pr_merge: mergeable}`). For that, `pr_merge` now says whether the host would merge the PR now, not only whether it conflicts: `mergeable | blocked | conflicting | unknown`, from GitHub's `mergeStateStatus` (CLEAN, UNSTABLE and HAS_HOOKS are `mergeable`; BLOCKED, BEHIND and DRAFT are `blocked`). Asking for `pr_approval: approved` and `pr_ci: passing` instead would hide Merge on every repo without required reviews or CI, where GitHub reports no review decision and no checks; the repo's own branch rules decide. `pr-remind` takes `blocked` as well as `mergeable`, since a missing review blocks the PRs it reminds about. Bitbucket nodes have no such status, so there `mergeable` still means only no conflict; the pill therefore says *no conflicts* for `mergeable` on both hosts and *no conflicts, merge blocked* for `blocked`. Merge is stricter than the old button, which showed for any item in the PR stage, conflicts and drafts included. Existing board files are not migrated: a board without `actions` on its PR stage has no Merge or Rebase buttons until they are added by hand.

88. **Escape closes the panel** (built; `App.tsx`, `BriefEditor.tsx`, `Info.tsx`, `DetailPanel.tsx`). Escape closes the item or plan panel like a click on the background, but not while the terminal has focus, a dialog or menu is open or a native select has focus; in the brief editor and Info draft it cancels that edit first, and it asks before closing while a brief or Info edit has unsaved changes, wherever the focus is.

89. **The stage dialog shows the stage's actions** (`api.rs::stage_source`, `StageSource.tsx`). A stage's actions (87) were only visible in its board file. `GET .../stages/{stage}/source` now returns `actions`, each `{label, when, confirm, args, source}` in board order, with `source` resolved by the same `StageFiles` the board problems use (84), so a missing skill or script shows the same message in both. `when` is sorted by key so its chips keep their order. The dialog shows them read-only in a third *What runs* tab, *Actions*, disabled when the stage has none; the tab falls back from skill / prompt to script to actions. Actions are still edited in `boards/<board>.json`.

## Pipeline decisions (original design)

The first design of the pipeline itself, before the UI. Its own numbers collide with the list above, so they are cited as P1 to P11 (decision 35 calls P11 "pipeline decision 11").

1. **State:** `stage:` in `workitem.md` frontmatter is the source of truth. Jira mirroring is a later add-on.
2. **Stages:** `analyze → ready_for_development → in_development → in_review → done`. "Blocked" is `agent_status: blocked: <reason>`, not a stage. `waiting: <what>` is an agent that idles on purpose (CI, a deploy) and needs nobody; its session is kept, and the notify hook only blocks it on a permission or elicitation prompt.
3. **Registry:** one `pipeline.json` in `~/.claude/skills/workitem-pipeline/`. It lists each stage with `handler`, `next` (allowed transitions) and `auto`.
4. **Transitions:** only `bin/workitem-move <workitem-dir> <stage>` changes `stage`. It checks the registry and the brief rule.
5. **Runner:** `/workitem-run`, one per repo, meant for `/loop 10m /workitem-run`. It only runs stages with `auto: true` (`analyze`, `in_development`). Pattern from `workitem-watch`: lock file `workitem-<dir>.running`, stale after 20 min, max 3 attempts, then `agent_status: blocked` and a push notification.
6. **Analyze mode** (`analyze`, UI decision 74). A new item starts in `analyze`; when `analyze_mode` is missing, `workitem-analyze` sets it first (there is no separate triage stage):
   - concrete steps, named files/layers, no open questions → `validate`
   - bug or Sentry error → `root_cause`
   - feature request → `clarify`
   - too vague → stay in `analyze`, `agent_status: blocked: <what is missing>`
7. **Review brief:** `analyze` writes a `## Review brief` section: root cause or decisions, plan, risk, size, test plan, assumptions, issue and system error links. `bin/workitem-move` refuses `ready_for_development` if a part is missing. A linked issue is required only where a stage's `require` has `issue: linked` (on the bundled board, `ready_for_development`); `workitem-move` refuses such a stage while `issue:` is `none`, and the skills ask for an issue only there.
8. **Approval:** `/workitem-approve <dir>` prints the brief, asks to confirm, sets `approved: true` and `approved_at`. Reject with a comment moves the item back to `analyze`. After approval it offers to start development.
9. **Intake:** manual. `workitem-create` accepts a Jira key, text, or a Sentry issue URL. New field `source: issue | system_error | text`.
10. **Existing skills:** `workitem-start` is the `in_development` handler and ends by moving to `in_review`. `workitem-watch` also moves an item to `done` when its PR is merged. Old `status` values migrate: `pending` → `ready_for_development` + `approved: true`, `in_progress` → `in_development`, `in-review` → `in_review`.
11. **Follow-ups:** work left for after the item is done goes in a `## Follow-ups` section, last in `workitem.md` (after `## Review brief`), one `- [ ]` line each. Agents never work on a follow-up. `analyze` and the development handler add one only when something has to happen after the item is done (a deploy step, a cleanup after a flag rollout, telling someone). Humans add and tick them by hand. Skills only append: they never delete, reword or untick a line, and skip one that is already listed. An open follow-up is an unticked line between `## Follow-ups` and the next `##` heading.

### Non-goals

Pull-based intake (Jira/Sentry polling), Jira status mirroring, cross-repo runner, central workitem store.

### Open points (decided during build)

- `analyze` is read-only for Sentry and the codebase. No production data access by default.

89. **Light/dark toggle** (`TopBar.tsx`, `theme.ts`, `main.tsx`, `styles.css`). The page followed only the OS theme. The top bar's last button now switches between light and dark (moon in light, sun in dark); until it is clicked the page follows the OS. The choice is per browser, `localStorage` key `workload.theme` (`light` or `dark`; absent follows the OS), not in `config.toml` or a workspace. There is no way back to following the OS in the UI other than clearing the key; a third state was not worth a menu. Each colour token is one `light-dark(light, dark)` pair on `:root`, so `color-scheme` alone picks the side: `light dark` by default, and `data-theme` on `<html>` pins it, which also switches scrollbars and native inputs. A small inline script in `index.html`'s head sets `data-theme` before the first paint (the module bundle loads too late for that), so no page paints in the other theme first, the terminal page included. A `storage` listener makes every open tab, terminal pages included, follow a toggle in another one.
