# ui/CLAUDE.md

Workload, the local web UI. The pipeline rules in the root `CLAUDE.md` still apply.

## Architecture

**UI backend** (`ui/backend`, axum, lib plus thin `main.rs`). It never writes `stage:` itself. It reads workitem files directly and shells out to `workitem-move` (with the full `workitem.md` path) for every stage change. Frontmatter fields it does own (approve, clear blocked) go through `workitem::set_fields`. Skills that need an LLM (`workitem-create`, `-start`, and the stage handlers) are launched by `launch::spawn` as `wi-*` tmux sessions running `claude --settings hooks.json <prompt>`. A workspace's `agent` in `workspace.toml` (one Claude-compatible executable, resolved on `PATH` at each launch) replaces `claude` for all its sessions (decisions 39, 52). An item session gets `WORKITEM`, `WORKITEM_FILE`, `WORKITEM_WORKSPACE` and `WORKITEM_REPO`, starts in its worktree or repo, and always gets `--add-dir <workspace>` (`launch::Scope::Item`); create and plan sessions start in the workspace folder with every board's repo added (`Scope::Workspace`). The launcher resolves a handler name to a `SKILL.md` (`launch::instructions`: `<workspace>/boards/<board>/skills/`, then `<workspace>/skills/`, then the bundled folder) and puts its body, plus a block with the stage and the allowed next stages, in the prompt. A stage can also carry an inline `prompt` instead of a `handler`. A stage's `model` (decision 60) becomes `--model` for every item session while the item is in that stage; without it no flag is passed. The prompt is one argv element and is never interpreted by a shell. tmux refuses commands over about 16 KB, so `launch::start` writes it to a private temp file that a fixed `sh -c` reads, deletes and appends as the agent's last argument. Keep it that way.

- `review.rs` turns the `pr_*` frontmatter keys into what the board shows of a PR (`PrStatus`) and serves the PR tab's conversation. Reading PRs and reacting to them are two scripts (decision 40). `watch/pr-status`, a workspace watcher, reads every PR of the workspace with `gh` and writes facts into the item (`pr_state`, `pr_ci`, `pr_ci_fix`, `pr_merge`, `pr_approval`, `pr_head`, `pr_unseen_comments`, `pr_checked_at`, ...). `watch/pr-review`, on the PR stage, reads only those keys: it moves merged PRs to the stage `on_merge` names and starts fixer sessions (`POST .../fix`, prompts in `launch.rs`) for conflicts, red CI (cap 3, once per head) and unseen comments or changes-requested reviews, and waits for a reading newer than the last fixer's end. A workspace with a board that has a PR stage but no `pr-status` in `workspace.toml` gets it implicitly. `WORKITEM_UI_GH` swaps the `gh` binary (passed to the script as `WORKITEM_GH`); tests use a stub.
- `dispatch.rs` keeps the session housekeeping (notify, reap) and then runs the column watchers; it reconciles every 5s and on `state.wake`. Starting handlers is a column watcher: `watch/run-items` (attempt cap of 3 kept as `handler_attempts` in the item, which `workitem-move` clears on every stage change; `once`; `when`) decides and calls `workitem-run-item`, which asks `POST .../run` (`dispatch::run_handler`) to launch. Stages written the old way (`auto` plus a handler or prompt) get that watcher implicitly.
- `AppState.busy` serialises session launches and dispatcher passes. Take it around any check-then-launch, or an item can start twice.
- A session belongs to a workspace only if its `@workitem_workspace` option equals the workspace folder (`tmux::session_for`), because session names carry no workspace; an untagged session belongs to none. `launch::start` sets it in the same tmux call that creates the session. Sessions without a workitem are `wi-new-*` (`tmux::is_agent_session`).
- `watch.rs` runs a stage's `watch` script (`every`, `command`, `args`) on a timer, whether or not the column has items; scripts live in `watch/` folders resolved like handlers (only scripts that cannot be shared belong in a board's or workspace's `watch/`; the generic ones stay bundled), run in the board's repo, get context in env vars (`WORKITEM_REPO`, `WORKITEM_DIR_ROOT` = the workspace folder, `WORKITEM_WORKSPACE`, ...) and the column's items as JSON on stdin, and last start times are kept in `watch.json`. A board can also carry a top-level `watch`; it gets every item of the board on stdin and no stage. `workspace.toml` can carry `[[watch]]` too (decision 55): it runs once per workspace in the workspace folder, with every item of the workspace on stdin and no board or repo. `watch/pr-status` and `watch/issue-status` (the Jira status of every item) belong there only; a board file that names them is invalid. An invalid `workspace.toml` keeps its last valid version (`config::Store`). The bundled `watch/age-out` deletes or moves old items, and `watch/pull-queue` is the queue (an `auto` stage with no handler gets it implicitly, every 5s). `bin/workitem-run-item <dir>` lets a script start an item's stage handler through the backend (`/run`, Bearer token). `watch/pr-status` and `watch/pr-review` keep everything in the workitem's frontmatter (`pr_*` keys, written through `bin/workitem_fields.py`). Rules belong in the scripts, not in Rust. A stage can be paused from its column header (`paused.json` in the root); `pass` skips its watchers until it is resumed.
- `plans.rs` holds planning sessions (decisions 36, 49): `wi-plan-<id>` sessions in the workspace folder with every board's repo added, no workitem, no worktree. The record `<workspace>/plans/<id>.md` is the source of truth; the agent writes it only through `bin/workitem-plan-note` (`--workitem` appends to `workitems`), and `launch::spawn_plan` passes inline `--settings` whose `PreToolUse` hook (`bin/workitem-plan-guard`) refuses edits outside the workspace folder. Not `--permission-mode plan`: it refuses the helper. The dispatcher marks plans whose session is gone `ended`; Resume runs `claude --resume <claude_session>`.
- `terminal.rs` runs `tmux attach-session` on a PTY (`portable-pty`) bridged to a WebSocket. Binary frames are keystrokes, text frames are `{"cols","rows"}` resizes. Closing the socket kills the attach client only; the agent session survives.
- `files.rs` backs the detail panel's Files tab: it lists the workitem folder, serves one file raw (with `Content-Security-Policy: sandbox`, because it shares the UI's origin), and reveals one in Finder (`open -R`; `xdg-open` on its folder elsewhere). It does not follow or list symlinks, and never leaves the folder.
- `auth.rs` guards everything: Host must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding), `/api` and `/ws` need the token cookie, and `/ws` also needs `Origin` equal to the Host. The token lives in `~/.workitems-pipeline/config.toml` (mode 0600); the workspaces are the folders in `workspaces/`, so there is no list to keep (`config::Store`).
- Behavior is tunable by env: `WORKITEM_UI_{HOME,PORT,TMUX_SOCKET,SKILLS,CLAUDE,GH,DISPATCH}` (see `AppState::new`, `Store::default_root`). `DISPATCH=off` matters for tests and for running a second instance.

**UI frontend** (`ui/frontend`, React, Vite, xterm.js). It polls `/api/*` every 3s; there is no push channel. Exactly one workspace is on screen (`?workspace=`, else the first); search is global. Pure state logic is in `boardState.ts`; it is kept apart from `Board.tsx` because the two names differ only in case and collide on macOS. Vite's dev proxy rewrites Host and Origin, since the backend rejects anything else.

## Testing approach

Backend integration tests (`ui/backend/tests`) run against a real tmux server on an isolated socket (`tmux -L`, see `tests/common`), the real `workitem-move` from `skills/`, and a stub `claude` script whose per-stage behavior comes from `<repo>/.stub-<stage>` files. The test world is a workspace `app` under a temp `Store` root with board `default` (the bundled one) for its repo. Do not mock tmux. Tests must not touch the default tmux server or a real config: use `AppState::new` and override fields.
